# TurboBaby — контекст для Claude Code

## Что это
Splinter — Telegram-бот учёта для аренды мотобайков (TurboBaby, Пхукет, владелец Филипп, 38 байков). Работает на этом сервере 24/7 как systemd-сервис `splinter`.

## Главные правила работы с этим проектом
- Режим автономии/стопов/логирования — см. раздел «РЕЖИМ РАБОТЫ» ниже (он главный).
  Кратко: локальные правки кода и диагностику делаю сам; стоп и «да» — только перед
  необратимым (деплой/push/restart/запись в рабочие таблицы/SQL/удаление). Дифф показываю
  в ревью (KB_review) перед деплоем, а не на каждую локальную правку.
- НИКОГДА не коммить и не пушить секреты: .env, memory.db, *.session. Они в .gitignore.
- После правки кода: предложи закоммитить в git, и напомни перезапустить сервис: `systemctl restart splinter`.
- Логи бота: /root/turbobaby-manager-bot/splinter.log
- Проверить статус: `systemctl status splinter`

## Бизнес-правила (НЕ нарушать в коде)
- Никаких массовых рассылок клиентам.
- Изменения в Google Sheets — только через approve-флоу.
- HONDA CLICK 125 не сдаём.
- Депозит = либо деньги, либо паспорт (не оба).
- Доставка только по Пхукету.
- Тайская команда (Пым) с клиентами не общается.

## Apps Script Bridge — какой проект «правильный»
Bridge — это Google Apps Script. Проектов несколько, легко перепутать. Признаки ВЕРНОГО:
- проект называется **«TurboBaby Bridge»**;
- его deployment обслуживает **BRIDGE_URL** (из .env); надёжнее всего — сверить deployment ID из BRIDGE_URL с Deploy→Manage deployments;
- его `ReadDocs.gs` содержит **И `setupCcLog`, И `setupReview`** (+ `setupBrain`, `handleReadDoc_`, `handleListBrain_`);
- файлы проекта: `Config/Bridge/BotData/ReadFleet/ReadClients/ReadFinance/ReadDocs/Booking.gs`.
Локальные `bridge_client.py` / `ReadDocs.gs` в репо — зеркало именно этого проекта.
Setup-функции (`setupBrain`/`setupCcLog`/`setupReview`) запускаются ВРУЧНУЮ из редактора —
строго в этом проекте, иначе ключ уйдёт в манифест чужого проекта (Script Properties у каждого свои).
Проверка после запуска: `list_brain` через Bridge должен показать новый ключ рядом с `cc_log`.

### 3. ЛОГИРОВАНИЕ (самосохранение прогресса). После КАЖДОГО значимого шага — строка в
`cc_log` (Doc `1o0be0v9xGI7L0tmpzpefgXBgq4jgmg2eM9lxL_Rlj2E`), новые записи СВЕРХУ:
- начал → `PLAN <UTC>: <суть>`;
- блокер (логин/доступ/ошибка) → `BLOCKED <UTC>: <что мешает, что нужно от Филиппа>`;
- завершил → `DONE <UTC>: <что сделано, commit hash если был, открытые хвосты>`.
Не коплю в голове — пишу сразу, чтобы Филипп и Claude-на-сайте видели прогресс без скриншотов.
Защита от затирки: запись = read_doc → прибавить сверху → write_doc; писать ТОЛЬКО если read вернул ok.

**WAITING-СТРОКА (лог должен отражать ВСЁ висящее на экране, не только сделанное).**
Дублирую в cc_log ЛЮБОЕ своё предложение/команду, которое кладу в поле ввода терминала Филиппу —
НЕ только то, что требует «да», но и просто «следующий логичный шаг». Как только подставил
что-либо в строку ввода — СРАЗУ пишу отдельной строкой:
- `WAITING <UTC>: [В ПОЛЕ ВВОДА ДОСЛОВНО]: <точный текст> | тип: <действие-ждёт-да / предложение-шага>`.
**В WAITING пишу ДОСЛОВНО тот же текст, что подставил в поле ввода — не пересказ, не сокращение,
а ТОЧНУЮ КОПИЮ символ-в-символ.** Если в логе пересказ, а в поле ввода другое — Claude-на-сайте
не сверит, что висит у Филиппа, и снова нужен скриншот. Дословная копия = он видит ровно то,
что на экране, скриншоты не нужны.
Филипп дакнул и выполнено → заменяю на `DONE <UTC>`. Отменил/стёр → `SKIPPED <UTC>: <что> отменено`.
Смысл: Филипп в термуксе только копирует/дакает, сам не печатает; Claude-на-сайте видит ТОЛЬКО лог,
не поле ввода. Без WAITING-строки он не знает, что у Филиппа висит на экране, и не может подсказать
«дакай / сотри». Закрывает слепое пятно — любое висящее предложение становится видно в логе.

- **ОДИН ШАГ = ОДИН DONE.** Не делаю два действия без записи между ними.
- **ЧЕСТНОСТЬ СТАТУСА — не выдавать непроверенное за проверенное.** Различаю в логе

  НЕ прогонял — пишу «ждёт функционального теста», а не «ПРОЙДЕНО». Филипп не программист, дакает

### ЗОНЫ СМЕЛОСТИ (заведено 7 июня 2026, переработано на 3 уровня) — максимум автономии
**Принцип:** вникание Филиппа в рутину опаснее автономной работы с бэкапом. Поэтому «да» осталось
ТОЛЬКО там, где параллельно работают живые люди и бэкап НЕ защищает (затирание чужого ручного труда).
Всё прочее — автономно: бэкап → действие → тест → отчёт постфактум. Аудитор (строится) постфактум
перепроверяет оранжевые действия — вторая страховка.

**🟢 ЗЕЛЁНАЯ — делаю САМ, молча, без бэкапа, только лог DONE:**
- **read-only диагностика — ВСЕГДА зелёная, НИКОГДА не требует «да»:** чтение логов
  (`splinter.log`), `grep`/`tail`/`cat`, `git status`/`git diff`/`git log`, `systemctl status`,
  read-only Bridge-запросы (ping/list/fleet), любой bash без записи. Автономно по умолчанию —
  Филипп НЕ должен жать Yes на чтение лога;
- `node --check` / `py_compile`, локальные правки кода в рабочей копии;
- запись в `cc_log` / `KB_review` — журнальные строки PLAN/DONE/NOTE/WAITING (мелкие, дописываются сверху);
- запись в **Bot Data** (это СВОЯ таблица бота: обслуживание/важное/аудит/транзакции бота).

**🟠 ОРАНЖЕВАЯ — делаю САМ, БЕЗ «да» Филиппа.** Цикл из 4 шагов:
1) **бэкап ПЕРЕД действием**; 2) выполнить; 3) **тест/проверка результата**; 4) **отчёт ПОСТФАКТУМ**
в лог + Филиппу: «сделал X, бэкап=Y, тест=прошёл/нет, откат=команда Z». Филипп НЕ подтверждает — читает отчёт.
- `git commit` + `git push` (бэкап = сам git; откат = `git revert <hash>`);
- `clasp redeploy` (бэкап = номер ТЕКУЩЕЙ версии ПЕРЕД деплоем; откат = `clasp redeploy` прошлой
  версии; именно `redeploy`, НЕ `deploy --deploymentId`);
- `systemctl restart splinter` (бэкап = текущий рабочий коммит + сервис `active` ДО; тест = статус
  `active`/`failed` + чистый старт в `splinter.log`; откат при `failed` = вернуть прошлый код и рестарт);
- синк рабочих Brain-доков `project_state`/`knowledge_base`/`faq`/`park_list` (`write_doc` перезаписывает
  весь док; бэкап = git-исходник `docs/*.md`; откат = ре-синк из git / version history);
- **SQL на `memory.db`** (бэкап = копия файла `memory.db` ПЕРЕД; откат = restore копии);
- **массовые операции** (прогон по списку; бэкап соответствующих данных ПЕРЕД).

**🔴 ТЁМНО-КРАСНАЯ — ТОЛЬКО запись/перезапись/удаление в ЖИВЫХ рабочих таблицах

- документация (`docs/*.md`, `CLAUDE.md`);
- синк базы знаний в Brain (`write_doc` доков `project_state`/`knowledge_base`/`faq`/`park_list`);
- журнальные строки в `cc_log` / `KB_review`.

**🟠 ОРАНЖЕВАЯ — по «да» Филиппа:**
- деплой / правка **КРУПНОЙ splinter-логики**;
- **спорные изменения ПОВЕДЕНИЯ** — если правка меняет бизнес-логику или поведение бота с людьми, спросить.

**🔴 КРАСНАЯ — строго «да» Филиппа КАЖДЫЙ раз:**
- Bridge `clasp redeploy` (деплой Apps Script);
- запись в рабочие таблицы (CRM / Зарплаты / Байки, `confirmed=true`; `set_fleet_oil` / `set_fleet_service`);
- `delete_event` / любое удаление;
- деньги / проводки Bot Data (транзакции);
- `sqlite3 memory.db` (UPDATE/DELETE/INSERT).

> Замечание о синке Brain: `write_doc` перезаписывает весь Drive-док — но это ЗЕРКАЛО git
> (истина = `docs/*.md`), откат = ре-синк из git, поэтому в редакции Б синк базы = 🟢
> (а не 🟠, как было в старом «РЕЖИМЕ РАБОТЫ»). Бэкап = git-исходник.

## ПРАВИЛО ОБНОВЛЕНИЯ БАЗЫ + АВТО-СИНК (17.06.2026, уточнено 18.06.2026)

База знаний ВСЕГДА должна отражать реальность, и синк НЕ должен требовать ручной команды каждый раз.

### 1. БАЗА = DEFINITION OF DONE (что обязательно фиксировать)
Любое изменение, влияющее на БУДУЩЕЕ понимание системы, Claude Code ОБЯЗАН отразить в
соответствующем `docs/*.md` **в рамках той же задачи, не откладывая**:
- решение Филиппа (выбор подхода, политика, договорённость);
- изменение бизнес-логики / правила;
- новый факт о парке / ценах / процессах;
- значимая правка ПОВЕДЕНИЯ бота (как он отвечает/действует с людьми).
Куда писать: `project_state.md` (состояние/что сделано/решения), `knowledge_base.md`
(правила/бизнес-логика/архитектура), `faq.md` (клиентские ответы), `park_list.md` (парк).
**Исключение:** мелкие технические правки кода (рефактор, багфикс БЕЗ смены поведения) — только
строка в `cc_log`, в базу НЕ обязательно. Задача НЕ закрыта, пока база не отражает значимое изменение.

### 2. АВТО-СИНК — ПОЛНОСТЬЮ АВТОНОМЕН, НИКОГДА не выносится на Филиппа
**ЦЕЛЬ: Филипп НИКОГДА не делает синк руками и НИКОГДА не отвечает на вопрос про синк. Это забота
Claude Code, целиком.**
- **КОГДА:** ТОЛЬКО по факту изменения любого base-дока (`project_state`/`knowledge_base`/`faq`/
  `park_list`) в рамках задачи. НЕ по расписанию, НЕ по регулярности. Пустой синк не гонять.
- **КАК:** синк делается САМ, МОЛЧА, как часть DONE — `write_doc(name=<ключ>)` + сверка по длине
  **code points** (drive == git). **НЕ спрашивать «синкнуть?», НЕ выносить отдельным шагом/вопросом/
  меню.** Просто сделать и в DONE написать «Brain synced» (или «delta 0», если совпало).
- **Если base-доки НЕ менялись** → синк не нужен: ничего не делать и **не упоминать** (CLAUDE.md/память —
  НЕ base-доки; их правка синка не требует).
- **Форма команды `write_doc` — чистая** (без `2>&1`/`||`/`;`/redirect/подстановки), чтобы guard не
  переспрашивал. Если guard всё же дёрнул на форму — это **НЕ повод выносить решение на Филиппа**:
  молча переформулировать команду в чистую форму и повторить.
- Истина = git (`docs/*.md`); Drive (KB_*) — зеркало, откат = ре-синк из git. Это 🟢.

### 3. PRUNE-ТРИГГЕРЫ — ПРО РАЗМЕР, НЕ ПРО СИНК
Ежедневные триггеры (`pruneCcLogTrigger` ~13:00 / `pruneReviewTrigger` ~13:10 / `pruneSessionsLogTrigger`
~13:20 UTC, cap 50k) держат ЖУРНАЛЫ (cc_log/review/sessions_log) компактными — отдельная гигиена размера.

### 4. ВЕЧНОЕ vs ХРОНИКА: project_state НЕ распухает (19.06.2026)
project_state РАЗДЕЛЁН на вечное + журнал сессий, чтобы физически не распухал:
- **`KB_project_state` (= `docs/project_state.md`) — ТОЛЬКО ВЕЧНОЕ:** состояние/правила/карты/ключевые ID +
  ФАКТЫ готовности компонентов («лестница 1-4.3 завершена», «Splinter работает»). Обновлять ТОЛЬКО при
  смене СОСТОЯНИЯ (новый компонент готов, правило/ID изменились). Не растёт (~17-35KB). В git — синхронно.
- **`KB_sessions_log` (Brain, ключ `sessions_log`) — ХРОНИКА сессий:** DONE-сводки сессий / диагностики /
  коммиты-история. Дописывается Claude Code; самочистится триггером (cap 50k, старое → `sessions_log_archive`).
  В git НЕ тащим (Brain-only).
- **ПРАВИЛО:** хронику (DONE-сводки сессий/диагностики/коммиты) писать в `sessions_log` (или cc_log —
  операционный шаг-журнал), НЕ в project_state. ФАКТ готовности → вечное; процесс «как сделали» → журнал.
  При сомнении — в вечное. (cc_log остаётся операционным PLAN/DONE-журналом per шаг, как и был.)

## ТЕСТЫ-ГЕЙТ перед прод-деплоем (пункт 4.3, заведено 18.06.2026)

Ни один прод-деплой не проходит при КРАСНЫХ тестах — кроме явного «да» Филиппа на обход.

- **Набор:** `tests/test_*.py` (9 шт, ~1.6с, всё мокнуто — нет ложного красного от флапа). Запуск гейта:
  `venv/bin/python3 gate.py`. Зелёные → `exit 0` (операция идёт); красный → `exit 1` (БЛОК) +
  пуш Филиппу + боевой_лог `result=blocked_by_tests`.
- **`git push` — железно:** нативный pre-push hook (`deploy/hooks/pre-push`, `core.hooksPath=deploy/hooks`)
  сам зовёт `gate.py`; красные → git РВЁТ push. На новой машине один раз: `git config core.hooksPath deploy/hooks`.
- **`clasp redeploy` / `systemctl restart splinter` — дисциплинарно:** ПЕРЕД ними прогнать `gate.py`,
  деплоить только при `exit 0` (нативного хука у них нет — это честный предел, на дисциплине).
- **ОБХОД — ТОЛЬКО по явному «да» Филиппа** (для ложного красного): `gate.py --override "причина"` →
  `exit 0` + боевой_лог `result=test_override` (факт обхода виден). Для push при обходе:
  `git push --no-verify` (+ запись через `--override`). **Claude Code сам обойти НЕ может.**
- **Зелёные операции** (Edit/локальный эксперимент) — НЕ гейтятся.
- Будущий дев-бот/оркестратор зовёт `gate.py` в деплой-пути и обойти не может — обход только Филипп.
- Тесты держать в `tests/` (НЕ временные `_*.py`-хелперы в корне — их gate не цепляет).

## ФОРМА КОМАНД (чтобы не триггерить встроенный guard Claude Code) — заведено 9 июня 2026

=== ФОРМА КОМАНД (чтобы не триггерить встроенный guard Claude Code) ===
Встроенный детектор инъекций форсит подтверждение на некоторых формах команд, даже если они в allowlist. Это НЕ отключается конфигом (--dangerously-skip-permissions снял бы и гейт боевой записи — ЗАПРЕЩЕНО). Поэтому пишем команды в форме, которая guard не триггерит:

1. ЧТЕНИЕ файлов: использовать абсолютный путь, БЕЗ cd и БЕЗ редиректов.
   ПЛОХО:  cd /root/turbobaby-bridge-gs ; grep -n X Bridge.js 2>/dev/null
   ХОРОШО: grep -n X /root/turbobaby-bridge-gs/Bridge.js
2. PYTHON-разведка/хелперы: НЕ heredoc (cat > f <<PY ... PY) со скобками/кавычками. Создавать скрипт Write-инструментом в файл, затем запускать по абсолютному пути:
   venv/bin/python3 /root/turbobaby-manager-bot/_recon.py
3. GIT в другом репозитории: git -C <dir> ..., НЕ cd <dir> ; git ...
4. ОДНА ПРОВЕРКА = ОДНА КОМАНДА В ОДНУ СТРОКУ. В проверочных командах НЕ использовать:
   `2>&1`, `2>/dev/null`, `>`/`>>` (редиректы), `||`, `&&`, `;`-цепочки, `$(…)`/`` `…` `` (подстановку
   команд), heredoc. Любая из этих форм триггерит встроенный guard → лишний переспрос.
   Нужен вывод — смотреть напрямую (`cat`/`grep` по абсолютному пути); нужен exit-код — отдельной строкой
   (`echo $?` без подстановки внутри другой команды). Несколько действий — несколько отдельных вызовов.
   ПЛОХО:  echo "ошибок: $(grep -c ERR log)"   ·   cmd1 && cmd2 ; cmd3 > out
   ХОРОШО: grep -c ERR /abs/log   (затем отдельной строкой следующая проверка)

Цель: технические читающие команды идут БЕЗ подтверждения. Гейт боевой записи (sqlite3 memory.db, clasp, confirmed=true в Лист1/CRM) — ОСТАЁТСЯ как есть, его НЕ обходим.

⚠️ ВАЖНО: запись в allowlist (`.claude/settings.local.json`) встроенный guard НЕ отключает — guard на ФОРМУ
команды отдельный механизм. Доказательство: в старом allow висели echo-`$(…)`-записи, но guard всё равно
переспрашивал. Поэтому переспросы на форме лечатся ТОЛЬКО чистой формой команды (пункты 1–4), а не allowlist.
Allowlist решает другое — КАКИЕ инструменты/команды разрешены без «да» (зелёная зона) vs под ask-гейтом
(красная/прод: sqlite3, clasp push/redeploy/deploy/run, git push, systemctl restart/stop).

## РАБОТА С ТЕЛЕФОНА (tmux) — заведено 17.06.2026

Чтобы Claude Code НЕ обрывался при потере связи в Termius (телефон уснул, метро, переключение сети),
работаем внутри постоянной tmux-сессии `cc`. Процесс живёт на сервере, даже если телефон отвалился.

**Рабочий цикл (простыми словами):**
- **Запустить сессию (первый раз):** `tmux new -s cc`
- **Внутри сессии — запустить Claude Code:** `cd /root/turbobaby-manager-bot && claude`
- **Отцепиться, НЕ закрывая работу** (после этого Termius можно гасить, телефон в карман): нажать `Ctrl+B`, отпустить, затем `D`
- **Вернуться (после обрыва или позже):** `tmux attach -t cc` — увидишь ровно то, что было, работа не прервалась
- **Список сессий:** `tmux ls`

**Автозапуск (настроено):** при SSH-входе сессия `cc` подцепляется сама (а если её нет — создаётся) —
строки в `/root/.bashrc` (срабатывает только для интерактивного SSH, не мешает скриптам). То есть обычно
достаточно просто зайти с телефона — попадёшь сразу в `cc`. Если случайно отцепился — `tmux attach -t cc`.

**Шпаргалка по Ctrl+B (префикс tmux):** `Ctrl+B` затем `D` — отцепиться; `Ctrl+B` затем `[` — режим
прокрутки (выход — `q`); `Ctrl+B` затем `C` — новое окно. Главное — `D` (detach) и `tmux attach -t cc`.

## ПУШ ПЕРЕД ОЖИДАНИЕМ РЕШЕНИЯ (заведено 17.06.2026)

Когда Claude Code ОСТАНАВЛИВАЕТСЯ и ждёт решения/«да» Филиппа — красная зона, спорный шаг ПОВЕДЕНИЯ,
выбор из вариантов, любой блокирующий момент, который МОЖНО предвидеть — ПЕРЕД тем как встать в ожидание
СРАЗУ слать пуш Филиппу в личку:
```
venv/bin/python3 notify.py --need "жду твоё решение: <что именно>"
```
(даст «🔧 жду твоё решение: <…> — нужно решение»). Чтобы Филипп не пропустил, что работа ВСТАЛА и
ждёт его, пока он отошёл от телефона.

- **ОБЯЗАТЕЛЬНО** на любой осмысленный «жду да / жду выбор / жду решение» — до начала ожидания, не после.
- Идёт ВМЕСТЕ с WAITING-строкой в cc_log (лог — для Claude-на-сайте; пуш — чтобы Филипп физически узнал).
- Связка: пуш о ЗАВЕРШЕНИИ блока (`--done`) уже есть (пункт 1 лестницы); это — пуш об ОСТАНОВКЕ-ожидании.
- **Честное ограничение:** встроенный guard движка Claude Code на ФОРМУ команды предвидеть программно
  НЕЛЬЗЯ — те редкие переспросы пушем НЕ покрываются. Но любой осмысленный, предвидимый «жду решение» —
  пушить обязательно.
- Зона 🟢 (пуш — не запись в таблицы).
