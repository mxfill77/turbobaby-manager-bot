# TurboBaby — контекст для Claude Code

## Что это
Splinter — Telegram-бот учёта для аренды мотобайков (TurboBaby, Пхукет, владелец Филипп, 38 байков). Работает на этом сервере 24/7 как systemd-сервис `splinter`.

## Главные правила работы с этим проектом
- Режим автономии/стопов/логирования — см. раздел «РЕЖИМ РАБОТЫ» ниже (он главный).
  Кратко: локальные правки кода и диагностику делаю сам; стоп и «да» — только перед
  необратимым (деплой/push/restart/запись в рабочие таблицы/SQL/удаление). Дифф показываю
  в ревью (KB_review) перед деплоем, а не на каждую локальную правку.
- НИКОГДА не коммить и не пушить секреты: .env, memory.db, *.session. Они в .gitignore.
- После правки кода: предложи закоммитить в git, и напомни перезапустить сервис: `systemctl restart splinter`.
- Логи бота: /root/turbobaby-manager-bot/splinter.log
- Проверить статус: `systemctl status splinter`

## Бизнес-правила (НЕ нарушать в коде)
- Никаких массовых рассылок клиентам.
- Изменения в Google Sheets — только через approve-флоу.
- HONDA CLICK 125 не сдаём.
- Депозит = либо деньги, либо паспорт (не оба).
- Доставка только по Пхукету.
- Тайская команда (Пым) с клиентами не общается.

## Apps Script Bridge — какой проект «правильный»
Bridge — это Google Apps Script. Проектов несколько, легко перепутать. Признаки ВЕРНОГО:
- проект называется **«TurboBaby Bridge»**;
- его deployment обслуживает **BRIDGE_URL** (из .env); надёжнее всего — сверить deployment ID из BRIDGE_URL с Deploy→Manage deployments;
- его `ReadDocs.gs` содержит **И `setupCcLog`, И `setupReview`** (+ `setupBrain`, `handleReadDoc_`, `handleListBrain_`);
- файлы проекта: `Config/Bridge/BotData/ReadFleet/ReadClients/ReadFinance/ReadDocs/Booking.gs`.
Локальные `bridge_client.py` / `ReadDocs.gs` в репо — зеркало именно этого проекта.
Setup-функции (`setupBrain`/`setupCcLog`/`setupReview`) запускаются ВРУЧНУЮ из редактора —
строго в этом проекте, иначе ключ уйдёт в манифест чужого проекта (Script Properties у каждого свои).
Проверка после запуска: `list_brain` через Bridge должен показать новый ключ рядом с `cc_log`.

## Деплой Bridge через clasp (замена копипасте, заведено 6 июня 2026)

- **Рабочая папка clasp:** `/root/turbobaby-bridge-gs` — ОТДЕЛЬНО от Python-репо
  (`clasp push` перезаписывает всю папку целиком; не смешивать с кодом бота).
  `.gs` тянутся/пушатся локально как `.js` (clasp v3) — это норма.
- **Аккаунт:** залогинен `info@turbophuket.com` (токены в `/root/.clasprc.json`, вне репо).
- **Script ID:** `12iXPDU_wxcyslItPW6X41ODuoVxx2smmlQBfhSwI6Lt42MTrYbv9HhOJ`.
- **Прод-деплой:** deploymentId `AKfycbxNC9gCM7-a635gDMk_jtPKsBNeCcBA23uuyrWXcMWHNREANzFSnpE1kXISAYZ_hXNOqw`
  — он обслуживает `BRIDGE_URL` (`/exec`). Сверка: id из BRIDGE_URL (между `/s/` и `/exec`)
  == этот deploymentId. Второй деплой `@HEAD` — тестовый (`/dev`), прод НЕ обслуживает, не трогать.
- **Штатный цикл** (из `/root/turbobaby-bridge-gs`):
  1. `clasp pull` — подтянуть актуальный прод-код (HEAD).
  2. правка `.js`.
  3. `clasp push` — заливает в HEAD (прод-URL пока не меняется — он на закреплённой версии).
  4. `clasp redeploy <deploymentId>` — обновляет СУЩЕСТВУЮЩИЙ прод-деплой новой версией,
     URL не меняется, Splinter не падает.
  5. Проверка: `ping` (v1.0.0, "alive") + `list_brain` (манифест с `cc_log`/`review`).
- **КРИТИЧНО** (каждое ломает прод):
  - Обновлять прод ТОЛЬКО `clasp redeploy <deploymentId>`. НЕ `clasp deploy` —
    в v3 это `create-deployment`, создаст НОВЫЙ деплой и сменит URL → Splinter отвалится.
  - Не плодить деплои; работать строго с прод-deploymentId выше.
  - clasp-папку держать отдельно от Python-репо; чужие проекты/.gs не трогать.
  - Нужен включённый Apps Script API: https://script.google.com/home/usersettings (одноразово).
- Прод важнее зеркала: при расхождении `/root/turbobaby-bridge-gs` (= прод) важнее `ReadDocs.gs` в репо.

## РЕЖИМ РАБОТЫ (применять во ВСЕХ задачах TurboBaby) — заведено 7 июня 2026
Этот раздел — главный над «Главными правилами» выше: он уточняет, где автономия, а где стоп.

### 1. АВТОНОМНОСТЬ. Безопасные шаги делаю САМ, без вопросов и без меню Yes/No:
- чтение любых файлов/таблиц/Drive, поиск, диагностика;
- `node --check`, `py_compile`, локальные правки кода в рабочей копии;
- запись PLAN/DONE/BLOCKED в `cc_log` и `KB_review`;
- запуск собственных вспомогательных скриптов (логирование, проверки).
НЕ переспрашиваю «что уточнить?» / «продолжать?» на безопасных шагах — делаю и логирую.

### 2. СТОП ТОЛЬКО ПЕРЕД НЕОБРАТИМЫМ. Классификация действий — в подразделе «ЗОНЫ СМЕЛОСТИ» ниже
(он главный по этому вопросу, уточняет/заменяет старый список). Кратко:
- «да» Филиппа = ТОЛЬКО 🔴 ТЁМНО-КРАСНАЯ зона = запись/перезапись/удаление в ЖИВЫХ рабочих
  таблицах Байки/CRM/Зарплаты (вкл. `set_fleet_oil`) — там параллельно пишут люди, бэкап не спасает;
- 🟠 ОРАНЖЕВАЯ (`git push`, `clasp redeploy`, `systemctl restart`, синк Brain-доков, SQL на `memory.db`,
  массовые операции) — делаю САМ без «да»: бэкап → действие → тест → отчёт постфактум;
- 🟢 ЗЕЛЁНАЯ (диагностика, локальные правки, cc_log/KB_review, Bot Data) — сам, молча.

### 3. ЛОГИРОВАНИЕ (самосохранение прогресса). После КАЖДОГО значимого шага — строка в
`cc_log` (Doc `1o0be0v9xGI7L0tmpzpefgXBgq4jgmg2eM9lxL_Rlj2E`), новые записи СВЕРХУ:
- начал → `PLAN <UTC>: <суть>`;
- блокер (логин/доступ/ошибка) → `BLOCKED <UTC>: <что мешает, что нужно от Филиппа>`;
- завершил → `DONE <UTC>: <что сделано, commit hash если был, открытые хвосты>`.
Не коплю в голове — пишу сразу, чтобы Филипп и Claude-на-сайте видели прогресс без скриншотов.
Защита от затирки: запись = read_doc → прибавить сверху → write_doc; писать ТОЛЬКО если read вернул ok.

**WAITING-СТРОКА (лог должен отражать ВСЁ висящее на экране, не только сделанное).**
Дублирую в cc_log ЛЮБОЕ своё предложение/команду, которое кладу в поле ввода терминала Филиппу —
НЕ только то, что требует «да», но и просто «следующий логичный шаг». Как только подставил
что-либо в строку ввода — СРАЗУ пишу отдельной строкой:
- `WAITING <UTC>: [В ПОЛЕ ВВОДА ДОСЛОВНО]: <точный текст> | тип: <действие-ждёт-да / предложение-шага>`.
**В WAITING пишу ДОСЛОВНО тот же текст, что подставил в поле ввода — не пересказ, не сокращение,
а ТОЧНУЮ КОПИЮ символ-в-символ.** Если в логе пересказ, а в поле ввода другое — Claude-на-сайте
не сверит, что висит у Филиппа, и снова нужен скриншот. Дословная копия = он видит ровно то,
что на экране, скриншоты не нужны.
Филипп дакнул и выполнено → заменяю на `DONE <UTC>`. Отменил/стёр → `SKIPPED <UTC>: <что> отменено`.
Смысл: Филипп в термуксе только копирует/дакает, сам не печатает; Claude-на-сайте видит ТОЛЬКО лог,
не поле ввода. Без WAITING-строки он не знает, что у Филиппа висит на экране, и не может подсказать
«дакай / сотри». Закрывает слепое пятно — любое висящее предложение становится видно в логе.

### 4. РЕВЬЮ ПЕРЕД ДЕПЛОЕМ. Перед необратимым шагом, затрагивающим код/таблицы:

строка «PLAN <UTC> ждёт ревью: <суть>». Жду ОК от Claude-на-сайте + «да» Филиппа.

### 5. ХВОСТЫ. Открытые задачи на потом веду списком в конце DONE-записи, чтобы не терялись между сессиями.

### Частые ошибки — не повторять (свод 7 июня 2026)
- **РАПОРТ = АДРЕС.** Всегда указываю КУДА записал: файл/лист/вкладка/колонка — не «в таблицу»
  обобщённо. Splinter пишет в Bot Data (вкладка «обслуживание»), НЕ в Лист1 Байки;
  в Лист1 col I («ТО Oil») — только через `set_fleet_oil` + `confirmed=true`.
- **ЛОГ СРАЗУ.** DONE в cc_log после КАЖДОГО шага ДО следующего. Сделал, но не залогировал =
  шаг НЕ существует для Филиппа (он в термуксе не печатает, узнаёт только из лога).
  7.06 это было нарушено — впредь нет.
- **ОДИН ШАГ = ОДИН DONE.** Не делаю два действия без записи между ними.
- **ЧЕСТНОСТЬ СТАТУСА — не выдавать непроверенное за проверенное.** Различаю в логе
  «технически готово» (сервис active, старт-лог ✅, py_compile) и «функционально подтверждено»
  (увидено в реале — карточка пришла, бот ответил/смолчал). Если Филипп дакнул вслепую и руками
  НЕ прогонял — пишу «ждёт функционального теста», а не «ПРОЙДЕНО». Филипп не программист, дакает
  вслепую → проверку формулирую за него, статус не завышаю.
- **Без `source` в командах.** НЕ пишу `source venv/bin/activate` (термукс просит «да» — `source`
  исполняется как shell-код). Питон зову напрямую: `venv/bin/python3 ...` (уже в allowlist, без подтверждений).

### ЗОНЫ СМЕЛОСТИ (заведено 7 июня 2026, переработано на 3 уровня) — максимум автономии
**Принцип:** вникание Филиппа в рутину опаснее автономной работы с бэкапом. Поэтому «да» осталось
ТОЛЬКО там, где параллельно работают живые люди и бэкап НЕ защищает (затирание чужого ручного труда).
Всё прочее — автономно: бэкап → действие → тест → отчёт постфактум. Аудитор (строится) постфактум
перепроверяет оранжевые действия — вторая страховка.

**🟢 ЗЕЛЁНАЯ — делаю САМ, молча, без бэкапа, только лог DONE:**
- **read-only диагностика — ВСЕГДА зелёная, НИКОГДА не требует «да»:** чтение логов
  (`splinter.log`), `grep`/`tail`/`cat`, `git status`/`git diff`/`git log`, `systemctl status`,
  read-only Bridge-запросы (ping/list/fleet), любой bash без записи. Автономно по умолчанию —
  Филипп НЕ должен жать Yes на чтение лога;
- `node --check` / `py_compile`, локальные правки кода в рабочей копии;
- запись в `cc_log` / `KB_review` — журнальные строки PLAN/DONE/NOTE/WAITING (мелкие, дописываются сверху);
- запись в **Bot Data** (это СВОЯ таблица бота: обслуживание/важное/аудит/транзакции бота).

**🟠 ОРАНЖЕВАЯ — делаю САМ, БЕЗ «да» Филиппа.** Цикл из 4 шагов:
1) **бэкап ПЕРЕД действием**; 2) выполнить; 3) **тест/проверка результата**; 4) **отчёт ПОСТФАКТУМ**
в лог + Филиппу: «сделал X, бэкап=Y, тест=прошёл/нет, откат=команда Z». Филипп НЕ подтверждает — читает отчёт.
- `git commit` + `git push` (бэкап = сам git; откат = `git revert <hash>`);
- `clasp redeploy` (бэкап = номер ТЕКУЩЕЙ версии ПЕРЕД деплоем; откат = `clasp redeploy` прошлой
  версии; именно `redeploy`, НЕ `deploy --deploymentId`);
- `systemctl restart splinter` (бэкап = текущий рабочий коммит + сервис `active` ДО; тест = статус
  `active`/`failed` + чистый старт в `splinter.log`; откат при `failed` = вернуть прошлый код и рестарт);
- синк рабочих Brain-доков `project_state`/`knowledge_base`/`faq`/`park_list` (`write_doc` перезаписывает
  весь док; бэкап = git-исходник `docs/*.md`; откат = ре-синк из git / version history);
- **SQL на `memory.db`** (бэкап = копия файла `memory.db` ПЕРЕД; откат = restore копии);
- **массовые операции** (прогон по списку; бэкап соответствующих данных ПЕРЕД).

**🔴 ТЁМНО-КРАСНАЯ — ТОЛЬКО запись/перезапись/удаление в ЖИВЫХ рабочих таблицах
Байки / CRM / Зарплаты** (там Пым/Даня пишут руками ПАРАЛЛЕЛЬНО — бэкап не спасёт от затирания их труда).
Только здесь нужно «да» Филиппа. Требуется: **«да» + бэкап + проверка «строка не менялась за последние 10 мин»**.
Оформляю РЕЗКО, отдельной строкой:
> `🔴 ЖИВАЯ ТАБЛИЦА — НУЖНО ДА:` <что именно пишем> → <куда: таблица/лист/колонка/строка> | бэкап=<что>
Сюда же `set_fleet_oil` в Лист1 Байки (живая таблица парка). Жду явное «да» Филиппа.
