## 💰 ЛОГИКА ЦЕН

### Шаг 1: Глобальная скидка по категории
В `'Календарь бронирования'!H3/I3/J3`:
- H3 — для Мотоциклы 1 (текущее: 15%)
- I3 — для Мотоциклы 2 (15%)
- J3 — для Скутеры (25%)

`цена_с_глобальной_скидкой = базовая_цена * (1 - глобальная_скидка_категории)`

### Шаг 2: Скидка за срок аренды

**Мотоциклы 1 (XSR, CB300, REBEL, MT-03, NINJA400):**
- 1-5 дней → 0%
- 6-13 дней → 5% + 1% за каждый день сверх 6 (макс ~12% на 13 дней)
- 14-30 дней → 25% + 1.5%/день сверх 13 (макс 45%)
- 30+ дней → 45%

**Мотоциклы 2 (VULCAN, CBR650, CB650, XSR900, R7):**
- 1-5 дней → 0%
- 6 дней → 10%
- 7-13 дней → 11% + 1%/день
- 14-30 дней → 18% + 2%/день
- 30+ дней → 50%

**Скутеры:**
- 1-5 дней → 0%
- 6 дней → 5%
- 7-13 дней → 6% + 1%/день
- 14-30 дней → 18% + 1.0625%/день
- 30+ дней → 35%

### Шаг 3: Депозит — два варианта на выбор

⚠️ **Только ОДНО из двух — либо деньги, либо паспорт. БЕЗ всяких +1500/день.**

1. **Денежный депозит** — стандартный (2,000-25,000 ฿ в зависимости от байка)
2. **Депозит-паспорт** — клиент оставляет паспорт вместо денег

**Правила использования депозит-паспорта:**
- **Скутеры с депозитом до 5,000 ฿** (PCX, NMAX, ADV 150/160) → паспорт **редко предлагаем**, обычно требуем деньги
- **Байки с депозитом 7,000 ฿** (XSR 155, XMAX, ADV 350) → **можно предложить паспорт**
- **Байки с депозитом от 15,000 ฿** (CB 300R, MT-03, NINJA 400, CBR 650R, CB 650R, VULCAN, XSR 900, R7, XADV 750) → **АКТИВНО ПРЕДЛАГАТЬ паспорт** — это удобнее клиенту чем большой кэш-залог

⚠️ Цена аренды от выбора депозита **НЕ зависит**. Тариф одинаковый.

**Депозит в валюте (USD / EUR) — уточнено 07.06.2026:**
- Денежный депозит можно принимать в долларах/евро. Сумму берём по модели из таблицы
  «Календарь бронирования» (в батах) → переводим в примерный эквивалент USD/EUR → **округляем до сотен**.
- Возврат — **тем же способом** и в той же зафиксированной сумме (пример из диалогов:
  «200 USDT — так зафиксировали, так и вернём»).
- Правило «депозит = деньги ИЛИ паспорт (не оба)» при этом НЕ меняется.

### Правила цен v2 (заведено 05.07.2026)

1. **Сезоны:** high season = **1 ноября – 15 мая**; low season = **16 мая – 31 октября**.
2. **Глобальная скидка** — ячейки `'Календарь бронирования'!H3/I3/J3`, крутит владелец РУКАМИ
   при смене сезона. Бот сезон сам НЕ вычисляет — читает эти ячейки (через 'цены альт' B2/B9/B19).
3. **Цена клиенту = текст колонки J Календаря дословно** — бот не пересчитывает и не «улучшает»
   число, называет ровно то, что даёт J за запрошенный срок. **Единственное исключение — кап-случай
   (п.4):** сработал кап-триггер → вместо J-числа называется оффер «от <кап> ฿/мес».
4. **Кап-триггер (акции low season):** блок капов на листе «Календарь бронирования» справа от
   H3/I3/J3 — «Модель | Кап ฿/мес | Активен(да/нет)», 12 моделей. Если кап по модели **активен**
   И цена по J за запрошенный срок **больше капа** → клиенту оффер:
   **«от <кап> ฿/мес — предложение низкого сезона»**. Bridge `quote_price` отдаёт поля
   `cap_price`/`cap_active` (только данные); логика подмены/оффера — на стороне userbot.
5. **Минимальные сроки аренды:** скутеры — от **5 дней**; мотоциклы — от **3 дней**;
   исключение **XSR155 — от 5 дней**. Запрос короче минимума → отвечаем
   «сдаём от N дней» + называем цену на минимальный срок.
6. **Несколько байков в одном запросе** → раздельные цены по каждому байку, ОДНИМ сообщением.
7. **Депозит при нескольких байках** снижается ТОЛЬКО через менеджера и ТОЛЬКО если клиент
   **сам спросил** про снижение — бот сам скидку на депозит не предлагает.

## ✅ ПРОЦЕСС ЗАКРЫТИЯ АРЕНДЫ (КРИТИЧНО!)

⚠️ **Никогда не нажимать "Завершена" просто потому что прошла дата возврата!**

Перед тем как переключить статус аренды на "Завершена" — бот ОБЯЗАН проверить **6 условий**. Если хотя бы **одно** не выполнено — **НЕ закрывать**, эскалировать Филиппу с конкретным вопросом что не так.

### Чек-лист закрытия аренды:

#### 1. ✅ Долги по аренде = 0
- Колонка **I** ("Долг") в листе "клиенты" должна быть пустая или 0
- Колонка **J** ("К оплате на данный момент") должна быть полностью покрыта **K** ("Оплачено")
- Если есть долг — **не закрывать**, сначала клиент должен доплатить или Филипп должен принять решение списать

#### 2. ✅ Байк физически возвращён (подтверждение в переписке с клиентом)
- В TG/WhatsApp переписке с клиентом должно быть **явное подтверждение** что байк передан обратно ("вернул", "отдал", "Pleum забрал", "встретились в офисе" и т.п.)
- Время возврата зафиксировано в чате
- Если переписки нет / клиент не отвечает — **НЕ закрывать**

#### 3. ✅ Фотоотчёт принятия байка
- Тайские помощники (сейчас — Pleum) при приёме байка делают **фотоотчёт**: состояние корпуса, пробег, бензин, шлемы, ключ/брелок
- Эти фото должны существовать (где-то в Google Drive / TG / WA)
- Если фотоотчёта нет — байк формально **не принят**

#### 4. ✅ Претензий от тайцев нет
- После приёма Pleum (или кто принимал) подтвердил: "всё ок, без повреждений, всё на месте"
- Если есть повреждения / царапины / разбит фонарь / разбит руль / потеряны ключи — это **отдельный процесс** (вычеты из депозита, согласование с клиентом)
- Только после **окончательного "всё ок"** можно идти дальше

#### 5. ✅ Депозит обработан
- **Если деньги:** возвращены клиенту (или вычеты согласованы)
- **Если паспорт:** возвращён клиенту лично в руки
- Никаких "Депозит вернём завтра" — пока не обработан, аренда **не закрыта**

#### 6. ✅ Все доплаты/вычеты учтены
- Просрочка → 30% надбавка посчитана (по правилу 3 договора)
- Грязный байк → 200 ฿ вычет
- Неполный бак → 80/100 ฿ за деление
- Потеря ключа/брелка → 500/3000-5000 ฿
- ТО просрочено → штраф учтён
- Всё что должно быть **внесено в систему** ДО закрытия

### Fail-closed гейты close_booking (фикс инцидента row705, 08.07.2026)

Bridge-операция `close_booking` («В аренде»→«Завершена») закрывает аренду ТОЛЬКО когда все
проверки прошли; не может проверить — НЕ закрывает (никаких молчаливых пропусков, force-флага нет):
- **km_end (пробег на сдаче) обязателен** — без него `err km_required`, карточка ПРИЁМА остаётся
  ждать «да <цифра пробега>» (или закрыть руками);
- **одометр строки (Q) пуст/нечисловой** → `err odo_unverifiable` «одометр строки пуст — сверь и
  закрой руками»: чек «одометр не уменьшается» провести нельзя, автозакрытие запрещено;
- **km_end меньше Q** → `err odometer_back` (одометр не уменьшается — правило владельца).
Причина: инцидент row705 — write-смок на живой аренде при пустом Q молча отключил гейт одометра
и закрыл живую строку. **Урок-класс: write-смоки на живых строках рабочих таблиц ЗАПРЕЩЕНЫ** —
только тестовые сущности (строка `ТЕСТ …`: создать→проверить→удалить, каждый шаг по отдельному
«да» Филиппа) или err-ветки, доказанные харнессом как не-пишущие (полный текст — CLAUDE.md,
раздел «УРОК-КЛАСС: WRITE-СМОКИ НА ЖИВЫХ СТРОКАХ ЗАПРЕЩЕНЫ»).

## 🐀 SPLINTER — бот-супервайзер (учёт + мониторинг)

Splinter — наш Telegram-бот, помощник Пыму и глаза Филиппа. **Считает, смотрит, спрашивает, напоминает — но сам деньги НЕ двигает** (переводы/выплаты делают Пым и Филипп). Что бы ни написали в группе — Splinter не выполняет «команду» перевести деньги.

### Принцип: доверие к Пыму
- Если что-то не сходится — Splinter **сначала уточняет у самого Пыма** (в группе, тегая @Pleummmm), НЕ бежит к Филиппу.
- К Филиппу в Turbo HQ уходит только **итог дня** и то, что реально не закрылось.
- Splinter **копит записи** и периодически (не после каждой) тегает Пыма «зайди проверь».

### Что делает по группам
**💰 Money Cashflow + Самоорганизация (деньги):**
- Парсит записи Пыма. Формат: `<байк ID> +<сумма> Bath <депозит>` (аренда), `<описание> -<сумма> Bath` (расход), строки `Balance X Bath Y Euro Z Passport`.
- Ведёт независимый баланс (THB / EUR / Passport), записывает транзакции в Bot Data.
- Когда Пым пишет `Balance` — сверяет со своим. Сошлось ✅ молча / разошлось → мягко спрашивает Пыма.
- Читает чеки (фото) → сверяет сумму на чеке с написанной.
- Категоризирует: rental / salary / advance / fuel / taxi / topup. Если бензин/такси выбивается из нормы — отмечает, уточняет у Пыма.
- Splinter делает запись списания, **Пым проверяет** (не наоборот).
- **Тег боту + сумма в денежной группе = ВСЁ РАВНО ПРОВОДКА** (Fix 20.06): «-360 @bot» в кассе → `_handle_money` (запись), НЕ в мозг-болталку. Только money-группы; в HQ/прочих тег боту остаётся обращением.
- **Подтверждение проводки шлётся с retry на сетевой таймаут** (`_send_retry`, 3 попытки): запись идемпотентна по msg_id, ретраится ТОЛЬКО доставка подтверждения (без задвоения). Причина: инцидент 09:43 — запись прошла, подтверждение упало ConnectTimeout → Пым не увидел.

**🔧 Обслуживание (การบำรุงรักษา):**
- Ловит факты: байк вернулся / сдан / в ремонте.
- Смотрит фото: есть ли топливо и пробег. Если не хватает — напоминает команде и зовёт Пыма.
- Пишет события в Bot Data (привязка к закрытию аренды, п.3 чек-листа).

**🛵 Delivery cooperation:**
- Следит за ходом выполнения доставок (выдача/возврат, адреса, статус).

### 🌐 ЯЗЫК И ФОРМАТ (важное правило)
- **Во ВСЕХ чатах где есть тайские сотрудники Splinter пишет на ДВУХ языках — тайский + русский.** Метки 🇷🇺/🇹🇭 для читаемости. Это правило по умолчанию для всех операционных групп (касса, обслуживание, доставка, отметка).
- **ЧИСТОТА БЛОКОВ (уточнено 11.06.2026):** 🇹🇭-блок — ЧИСТЫЙ тайский (никакой кириллицы — даже «ТО»/«ТО Oil»/русские названия работ переводятся: `เปลี่ยนน้ำมันเครื่อง` и т.п.); 🇷🇺-блок — чистый русский. Языки НЕ чередовать построчно — монолитные блоки, один флаг на блок. Между блоками — **единый разделитель** (пустая строка), вставляется ЦЕНТРАЛЬНО в `_send` (идемпотентно) → одинаков везде: сводка, карточка, квитанции, вопросы, служебные сообщения. Аудитор метит `style_issue` при кириллице в тайском блоке и при неполной двуязычной структуре.
- **СВОБОДНЫЕ ответы тайцам = ВАРИАНТ 1 (RU основа → TH перевод, в проде с 24.06.2026):** для НЕшаблонных сообщений (damage-вопрос Пыму, пины важного/ТО) русский генерится первым, тайский = ДЕТЕРМИНИРОВАННЫЙ перевод этого RU одним вызовом (`splinter._translate_ru_th` / `bilingual_from_ru` / `bilingual_pin`, промпт `TRANSLATE_RU_TH`) — смысл/конкретика (детали, числа, депозит) гарантированно совпадают. Контракт LLM-инструментов `flag_important`/`set_pin`/`pin_reminder`: `pin_text` отдаётся НА РУССКОМ, код переводит. Шаблоны `msg_*` уже парные — их не переводим. Раньше TH генерился отдельно и беднел/расходился с RU.
- **ТЕХНИКА = БАЙК, не «автомобиль»:** запрещено называть мотобайк «автомобиль/машина» (тайск. `รถยนต์`) — только «байк/мотоцикл/скутер» (`รถมอเตอร์ไซค์/รถ`). Защита: в промптах (vision/system/инструменты) + пост-фильтр `_no_car` на RU и TH. Аудитор метит `style_issue` при «автомобиль/машина/รถยนต์» и при сильном расхождении длин (TH < 40% RU = вероятно неполный перевод).
- **Диалог с владельцем (Филипп):** когда Филипп обращается к Splinter (тег `@turbobaby_manager_bot` или ответ на его сообщение) в любой группе — Splinter:
  1. **дублирует запрос Филиппа** на двух языках (🇷🇺/🇹🇭),
  2. затем **отвечает** на двух языках,
  3. это работает для текста тоже (не только для голосовых).
- **Не показывать баланс Самоорганизации (мелкой кассы) в основном потоке Money Cashflow** — в каждом кошельке только его собственный баланс. Касса — в группе Самоорганизации, Cashflow — в Money Cashflow.

### Регламенты ТО и обслуживания (live-обкатка, 30-31 мая 2026)
- **ИНТЕРВАЛ ЗАМЕНЫ МАСЛА зависит от типа байка:**
  - **Скутеры (NMAX, XMAX, ADV, FORZA, PCX) → каждые 4000 км**
  - **XADV и мотоциклы (XSR, CB, CBR, MT-03, NINJA, VULCAN, R7, REBEL) → каждые 5000 км**
  - (Ранее ошибочно стоял дефолт 6000 — исправлено 31.05.2026 по указанию Филиппа.)
- **ПРОЧИЕ РЕГЛАМЕНТЫ ТО (уточнено Филиппом 07.06.2026):**

  | ТО | Интервал | Для кого |
  |---|---|---|
  | Моторное масло | скутеры 4000 км / мотоциклы+XADV 5000 км | все (по типу байка, см. выше) |
  | Gear oil (масло редуктора) | ТОТ ЖЕ, что моторное масло (на скутерах = 4000 км) | ТОЛЬКО скутеры (у мотоциклов/XADV редуктора нет) |
  | ABS oil (кол.K) | 10 000 км | ВСЕ байки |
  | Воздушный фильтр (кол.L) | 20 000 км | ВСЕ байки |
  | Масляный фильтр | 20 000 км (СПРАВОЧНО — столбца НЕТ → в историю «события») | ВСЕ байки |

  **Машиночитаемый блок (бот читает интервалы отсюда через read_doc; при сбое чтения — фоллбэк на хардкод):**
  ```json SERVICE_INTERVALS
  {
    "oil": {"scooter": 4000, "moto": 5000},
    "gear": {"scooter": 4000, "moto": null},
    "abs": 10000,
    "airfilter": 20000,
    "oilfilter": {"ref": 20000, "note": "столбца нет → история"},
    "scooter_keywords": ["nmax", "xmax", "adv", "forza", "pcx", "click"],
    "moto_default": 5000
  }
  ```
  - Тип байка: scooter = в названии есть слово из `scooter_keywords`; иначе moto. **XADV → moto** (масло 5000; gear НЕ трекается). `gear.moto = null` → у мото/XADV редуктор не трекаем.
  - ⚠️ Фаза 2 (J/K/L): расчёт срока + напоминания для gear/ABS/возд.фильтра — зеркало масляного флоу. Масляный фильтр (столбца нет) остаётся в истории «события». Кол.I (моторное масло) — как было. Интервалы бот берёт ИЗ этого блока, хардкод-дубли в коде = фоллбэк при флапе Docs.
- **Источник пробега последней замены масла — колонка I «ТО Oil»** в Листе1 Байки (НЕ колонка J «ТО Gear» — это замена ремня/шестерён, другое!). Колонка H = пробег при покупке (стартовый), не текущий.
- Расчёт: следующее ТО = (ТО Oil из колонки I) + интервал по типу. Текущий пробег — из фото одометра темы.
- **После любого ТО** (масло/резина/ремонт) — обязательно фото текущего пробега + отчёт/чек от сервиса.
- **Критичные напоминания** (просрочка ТО, замены) — крепить коротким сообщением, повторять раз в 5 дней; после выполнения убирать из закрепа.
- **Двуязычный закреп** в чатах-темах по байкам (как в сообщениях: тайский + русский).
- Пробег ведётся СТРОГО внутри каждой темы отдельно (тема = байк), темы не смешивать.
- Факт 31.05: NMAX 4957 — ТО Oil(I)=30800, интервал 4000 → следующая на 34800, текущий 35814 → ПРОСРОЧЕНО на 1014 км, менять масло.
- Факт: XMAX 4724 — ТО Oil=14900, интервал 4000 → следующая 18900, текущий 19705 → ПРОСРОЧЕНО ~805 км.

### 🗃️ СИСТЕМА УЧЁТА ОБСЛУЖИВАНИЯ — 2 регистра (актуально на 11.06.2026)
Модель Филиппа = **два регистра**, их НЕ путать:

**Регистр 1 — РАБОЧИЙ (столбцы I/J/K/L Лист1 «Байки»):** данные с РАСЧЁТОМ срока ТО (последний пробег → `next_km` → статус ok/due/overdue → напоминание). Пишется guarded-экшенами по «да» доверенного. Карта столбцов (прочитана по живому листу):

| Столбец | Что | Интервал | Экшен записи |
|---|---|---|---|
| **H** | Пробег при покупке (стартовый) | — | НЕ трогаем |
| **I** | ТО Oil — моторное масло | скутеры 4000 / мото+XADV 5000 | `set_fleet_oil` |
| **J** | ТО Gear — редуктор/ремень/шестерни | = масло (только скутеры) | `set_fleet_service kind=gear` |
| **K** | АБС — ABS oil | 10 000 (все) | `set_fleet_service kind=abs` |
| **L** | Аир фильтр — воздушный | 20 000 (все) | `set_fleet_service kind=airfilter` |

**Регистр 2 — «СОБЫТИЯ» (инфо-сноска, Bot Data, БЕЗ интервала/расчёта):** работы, у которых нет столбца с расчётом — масляный фильтр, тормозные колодки, цепь, грипсы, тормоза, свечи, аккумулятор, шины, прочее. Записываются строкой «<работа> — <км> км» (`add_event`), показываются в карточке байка (`read_events`), чистятся `delete_event` по точному ключу. Источник истины расчёта ТО — ТОЛЬКО регистр 1.

**Классификация работы в коде:** `_classify_work` → `oil` (кол.I) | `gear` (J) | `abs` (K) | `airfilter` (L) | `info` («события»). Бот берёт интервалы из машиночитаемого блока `SERVICE_INTERVALS` выше (через `read_doc`, кэш ~10 мин), при сбое чтения — фоллбэк на хардкод `_SVC_INTERVALS_FALLBACK` (расчёт ТО не должен падать при флапе Docs).

### ЗАКРЫТИЕ ТО — автомат после замены масла (в проде с 9 июня 2026)
Когда масло реально заменили, Splinter сам предлагает закрыть ТО и записать новый «ТО Oil» в Лист1 кол.I,
а не долбит «просрочка». Поток (фиксы A/B/C):
- **Триггер (фикс A):** в теме байка слова про масло/замену (`заменили/поменяли/เปลี่ยนน้ำมัน/oil`) **И**
  фото приборки с распознанным пробегом. Тогда вместо «просрочка X» бот спрашивает
  «🔧 Масло заменили на <байк>? Записать новое ТО Oil = X км? да/нет» (двуязычно RU/TH).
- **Сторож пробега (фикс B):** распознанный с фото пробег сверяется с последним известным по теме.
  Если новый < последнего (одометр не убывает — ошибка vision, напр. 31844 при прошлом 37000) → бот
  НЕ пишет, а просит правильное число/переснять. До корректной цифры в ТО/Лист1 ничего не уходит.
- **Авторизация записи = ТОЛЬКО доверенные:** боевую запись в Лист1 (кол.I) запускает «да» от **Пыма
  или владельца** (`TRUSTED_AUTHORS`). «Да» от техника (Earth и пр.) НЕ пишет — бот отвечает
  «запись подтверждает @Pleummmm или владелец, @Pleummmm подтвердите…» и держит запрос открытым 30 мин,
  ждёт «да» доверенного. «нет» от любого → трактуется как обычный контрольный замер (сверка/просрочка).
- **Запись:** `set_fleet_oil(номер, пробег, confirmed=true)` — пишет РОВНО колонку I по голому номеру байка
  (последнее число ≥3 цифр, минус кубатура: «NINJA 400 6334» → `6334`). Защиты: oil_decreasing (новое<старого),
  ambiguous (несколько байков), not_found — отказ без записи. Колонки H (стартовый) и J (Gear) НЕ трогаются.
- **После успеха:** «✅ ТО Oil обновлено: <байк> → X км, просрочка закрыта» + снятие закрепа-напоминания
  (открепляет pinned + закрывает открытое «важное» по теме).
- **dirt в сервисе (фикс C):** совет «помыть/воск/чехол» НЕ шлётся, когда байк в сервис-контексте
  (замена масла / ремонт / чек сервиса) — байк чинят, а не моют. Грязь распознаётся как прежде, гасится только совет.
- ВАЖНО: `service_upsert` (Bot Data вкладка «обслуживание») и запись «ТО Oil» в Лист1 (`set_fleet_oil`) —
  РАЗНЫЕ вещи. Трекер только читает кол.I как точку отсчёта; обновляет кол.I ТОЛЬКО `set_fleet_oil` по «да» доверенного.

### Двухфазный сервисный поток ТО (в проде с 23 июня 2026)
Механик (Earth, НЕ доверенный) ТРИГГЕРИТ обе фазы; запись в Лист1 — по-прежнему ТОЛЬКО по «да» доверенного
(Пым/владелец). trust НЕ ослаблен. Состояние визита — Bot Data вкладка **«то_заявки»** (переживает рестарт).
- **ФАЗА 1 (заявка):** механик «привёз <байк> на масло/фильтр/редуктор» (`event_type==intake`) → бот фиксирует
  НАМЕРЕНИЕ (status=`заявлено`, declared=перечень), в Лист1/обслуживание НИЧЕГО не пишет, отвечает
  «принял, отпишись когда закончишь».
- **ФАЗА 2 (факт):** механик отписался «готово» → если перечня нет → бот ПЕРЕСПРАШИВАЕТ «что сделал/не сделал?
  одометр?»; получив перечень факта + одометр → status=`ждёт_подтверждения` + поднимает доверенному
  inline-кнопку «✅ Подтвердить запись @Pleummmm» (сделано/не сделано/одометр).
- **Запись (по «да» доверенного):** на КАЖДУЮ сделанную позицию — oil→`set_fleet_oil` (кол.I),
  gear/abs/airfilter→`set_fleet_service` (кол.J/K/L), всё `confirmed=true` под сторожем `*_decreasing`;
  фильтр/колодки/цепь — в «события» (регистра «след. замена» нет). Сразу после каждой записи —
  `service_upsert` синк «обслуживания» (закрывает разрыв _write_oil→обслуживание). Затем заявка `закрыто`.
  Запасной путь: доверенный присылает ЧИСЛО вместо кнопки → пишем сразу его одометром.
- **Синк зеркала решает ПЕРЕЧИТАННЫЙ ФАКТ, а не флаг расписки (13.08.2026, `write_fact.py`).**
  Писчее плечо моста делает одну отправку без пересылок, поэтому отказ расписки отдаёт
  `outcome='unknown'` и требование перечитать факт: величина в Лист1 могла ЛЕЧЬ. Прежний
  `if r.get("ok")` этого не знал и гасил синк — 13.08 так потерялись две строки зеркала
  (4957 abs 37015 и 4724 abs 20747; в Лист1 обе величины стоят). Теперь после неудачи записи —
  и только после неё, здоровый путь не платит ни одного лишнего обращения — перечитывается
  целевая клетка (`fleet(cells=1)` + контракт клетки): величина стоит → синк идёт и позиция
  считается записанной; в клетке другое или пусто → синка нет; **клетку прочитать не удалось →
  «неизвестно», записанным НЕ считается**. Отказ, вынесенный самим мостом (`not_confirmed`,
  `*_decreasing`, `not_found`…), перечитывания не вызывает — исход там определён.
- **Висяк:** заявка без отписки результата старше ~6ч → авто-напоминание механику (раз в час, throttle).
- **Сосуществование:** старый одно-фазный вопрос [После замены]/[Просто пробег] НЕ заменён — гейтится
  по наличию открытой заявки (если заявка есть — фаза-2 владеет записью; иначе старый флоу как был).
- **Замки/аудит:** `set_fleet_*` остаются в _REDZONE (4.1 чёрный ящик + 4.2 токен-замок). `service_upsert`
  добавлен в client-side `_REDZONE_ACTIONS` (аудит 4.1, НЕ 4.2). Эндпоинты `service_pending_*` — своя
  таблица, вне REDZONE_LOCK. В «события» добавлена колонка `sender` (кто прислал).

### ПРАВКА И ОТКАТ ОШИБОЧНЫХ ЗАПИСЕЙ — штатная операция (4 августа 2026)
Владелец рулит с телефона, поэтому ручная правка ячейки в таблице как способ починки данных
неприемлема. До 04.08 починить уже записанную ошибку было нечем: у моста не было экшена правки
строки ВООБЩЕ (только добавить/удалить), а сторож `oil_decreasing` блокировал даже подтверждённое
человеком понижение пробега. Что действует теперь:
- **Правка строки «события» — НА МЕСТЕ (`edit_event`), а не «удалить + добавить заново».**
  Пересоздание теряло `recorded_at` (метку времени ЗАПИСИ) и уводило строку в конец листа —
  история переставала быть историей. Метка не правится ВООБЩЕ (её нет в белом списке полей, ни
  одна ветка в кол.A не пишет), а **ключ приводится к содержимому** отдельным полем `new_msg_id`:
  у автоматики ключ КОНТЕНТНЫЙ (`info:<номер>:<работа>:<км>`), и число, поправленное без ключа,
  оставило бы дедуп сверять строку по несуществующему отпечатку. Новый ключ проверяется на
  конфликт с чужой строкой. Дисциплина точного ключа — как у удаления: без ключа отказ, совпало
  больше одной строки → отказ (правку наугад не делаем).
- **Понижение пробега в Лист1 — по ветке «исправление ошибки».** Обычный путь НЕ ослаблен:
  понижение без названной причины и автора → прежний `oil_decreasing`. Ветку открывает ТОЛЬКО
  пара «причина + автор» (полумера не открывает). **Правило владельца сохранено: понижение больше
  500 км подтверждает Пым или владелец** (`trusted`), порог зеркалит `_SOFT_ODO_THRESHOLD`.
- **Аудит-след обязателен — «что было, что стало, кто исправил».** У события след лежит В САМОЙ
  СТРОКЕ (штамп в `notes`, `status=corrected`) плюс строка боевого журнала. У пробега места под
  след в живой таблице нет, поэтому след FAIL-CLOSED: журнал не записался → запись ОТКАТЫВАЕТСЯ
  (исправление без следа неотличимо от порчи данных).
- **Откат описан данными:** ответ обеих операций несёт готовый обратный вызов (`rollback` /
  `rollback_oil`) — вернуть прежнее значение можно тем же экшеном, руками в таблицу лезть не нужно.
- **Обе операции — высшего вида:** карточка владельцу с объектом и числом (`edit_event` — красный
  токен гарда), токен-замок 4.2 и чёрный ящик 4.1. Чтение истории (`read_events`) теперь отдаёт
  `msg_id`/`group`/`status` — иначе адресовать правку было нечем.
- Тесты: `tests/test_record_fix.py` + два node-харнесса на живом коде моста (в гейте).
  Подробности и остатки (деплой Apps Script — красная зона владельца; ручки в Telegram нет):
  `docs/artifacts/2026-08-04-record-fix-and-rollback.md`.

### ВЫДАЧА → активация брони (O3-3a, 8 июля 2026)

  по байку, read-only) и шлёт карточку подтверждения в группу «Входящие брони»:
  «🏍 ВЫДАЧА: байк → клиент, бронь строка N (даты). Активирую (Бронь→В аренде)? да / нет».
- Авторизуют ТОЛЬКО INTAKE_APPROVERS (владелец + Даня/Даша); Пым/тайцы НЕ авторизуют (§9 — тайская
  команда с клиентами не общается). «Да» → красный шаг под токен-замком 4.2 → Bridge `activateBooking`
  (bike+name+**date_start** — точный матч при двух бронях клиента, O3-2a) → «✅ В аренде, строка N».
  Ошибка Bridge → честный отказ «статус не менял — переведи руками». «Нет» → отмена без записи.
- Брони в CRM нет → «⚠️ брони не нашёл — активируй руками», handover-путь НЕ падает. Строка уже
  «В аренде» → молчание (активировать нечего). Анти-дубль карточки по строке брони + TTL запроса 30 мин;
  повторные ⚠️ по байку не чаще 10 мин. «Да» при живой карточке брони intake по-прежнему ставит бронь
  (приоритет не сломан). Тесты: `tests/test_handover_activation.py` (в гейте).

### ПРИЁМ → закрытие аренды (O3-3b фаза II, 8 июля 2026)
- На return-контексте (возврат в «Обслуживании») Splinter ДОПОЛНИТЕЛЬНО к листу закрытия (closing_upsert
  Bot Data + пинг Пыму — путь НЕ тронут) резолвит строку CRM (последняя В аренде/Завершена по байку,
  read-only) и шлёт карточку в «Входящие брони»: «📥 ПРИЁМ: байк вернулся от клиента, строка N. Пробег
  на сдаче: из return-контекста (нет → просит «да <цифра>»). Итог закрытия: из листа закрытия, если
  числовой >0. Завершаю (Завершена + пробег + оплачено)? да / нет».
- Авторизуют ТОЛЬКО INTAKE_APPROVERS. «Да» → красный шаг под токен-замком 4.2 → Bridge `closeBooking`
  (bike+name+date_start; km_end → кол.N — цифра в ответе авторизатора перекрывает контекст; paid_total →
  кол.K ТОЛЬКО если итог листа закрытия числовой >0) → «✅ Завершена, строка N». Ошибки Bridge
  (not_active/not_found/ambiguous/odometer_back…) → честный отказ «статус не менял — заверши руками».
  `unknown_action` (прод-Bridge ещё без деплоя фазы I) → «⏳ не задеплоено, карточка останется» —
  запрос ЖИВ, после Termux-деплоя то же «да» закрывает. «Нет»/«не завершай» → отмена без записи
  (отказ проверяется ПЕРВЫМ — «не завершай» не путается с «заверш»).
- Строки «В аренде» нет → «⚠️ заверши руками», возврат НЕ падает. Последняя строка уже «Завершена» →
  молчание (идемпотентность повторной return-фразы). Анти-дубль по строке + TTL 30 мин; ⚠️ не чаще
  10 мин. Приоритет «да» между карточками: бронь intake → активация выдачи → закрытие приёма
  (ветки выше перехватывают своё, не путается). Тесты: `tests/test_return_close.py` (в гейте).

### Аудитор — надзор за ботом (live-обкатка, 1 июня 2026)
Второй логический слой (модуль `auditor.py`), который НЕ доверяет Splinter и сверяет его работу с ФАКТАМИ (Bot Data, Лист1, memory.db) и правилами KB. Гибрид: детерминированные проверки + LLM на сложное.
- **Что ловит:** галлюцинации («сказал записал правило» → в memory.db нет), ложные рапорты («закрепил важное» → в листе нет/без msg_id), ошибки логики (ТО интервал 6000 вместо 4000/5000), запись пробега с фото без подтверждения.
- **Качество общения:** смешение языков (кириллица в тайском блоке и наоборот), неполная двуязычная структура (нет одного из блоков), эмодзи вместо слов (паспорт/деньги). Детектируется по диапазонам символов Unicode, без LLM. Глубокие странности перевода (смысл/транслит/тон) — опц. через LLM в отчёте.
- **Принцип:** сверяет требование→результат на основе реальных вводных (запрос + данные + правила), а не «второе мнение модели». Вердикты считаются детерминированно, LLM — только для резюме.
- **Журнал:** лист `аудит` в Bot Data (запрос, инструмент, аргументы, заявленный результат, вердикт, severity, предложение правки, статус).
- **Действия при находке:** только флаги + предложения правок. Сам НЕ правит память/правила — применяется после апрува Филиппа.
- **Отчёт:** раз в сутки в HQ (09:30) + по команде `/audit` (за 7 дней). Каждое действие бота проверяется сразу после выполнения (realtime-лог в журнал), сводка — раз в день.

### Диалог с владельцем = приоритет
- Филипп может в любом чате дать новую вводную/правку — Splinter принимает её (через `remember_rule` — как правило, или `save_note` — как заметку) и подтверждает.
- Правила глобальные (применяются во всех чатах через мозг).
- **Контекст ДАННЫХ — узко по теме группы** (каждая группа = своя тема: касса/обслуживание/доставка/отметка). Глобальные бизнес-данные и финансы Филипп получает ТОЛЬКО в Turbo HQ. В денежной группе «баланс» = наличные кошелька (`get_wallet_balance`), НЕ финансы бизнеса (`get_finance`).
- **Обучение — всегда:** узкий контекст данных НЕ мешает учиться. Новое правило/вводную можно дать в любой группе по любой теме — Splinter всегда принимает и запоминает.

### Архитектура (два процесса, один мозг)
- **Юзербот @turbophuket** (Telethon) и/или **официальный бот** — слушают группы.
- Решение: Splinter = **официальный бот** (явный, безопасный, как @Turbobabyre раньше), добавлен в группы как админ с Privacy Mode OFF.

- Память правил/заметок: SQLite `memory.db` (быстрый кэш) + дублирование важного в Drive.

### Уроки-классы дев-контура (ночь 11–12.07.2026)
- **LLM-детект юнитами не закрывается — только живой прогон.** Юнит-тесты с мокнутым LLM доказывают
  маршрутизацию, но не сам детект: поведение LLM/детектора на живых фразах проверяется ТОЛЬКО живым
  прогоном; golden-набор = ДОСЛОВНЫЕ фразы реальных клиентов, не придуманные «идеальные» формулировки.
  Пример ночи: модель-гард глушил прайс-сетку по всему окну диалога (корень фикса 1ed85df) — юниты
  при этом были зелёные.
- **Короткие алиасы моделей в `claude -p` дают 404.** CLI принимает только полные model id; короткий
  алиас в конфиге → 404 от API. Правило: в конфиги/кондукторы писать полные id либо нормализовать
  алиасы на импорте (фикс ПК-репо b18ad08).
- **`load_dotenv(override=False)` не перебивает застрявший env.** Демоны наследуют окружение
  родителя через рестарты: старое значение переменной «прилипает» в env процесса, и обновлённый
  .env его НЕ перебивает (дефолт override=False). Симптом «флаг в .env поменяли, а поведение
  старое» → сверять ЖИВОЙ env процесса, не только файл.
- **ТЗ для CC/Cowork-сессий — нейтральная лексика.** Густая терминология вида «токены/секреты/ключи»
  в тексте ТЗ триггерит защитные фильтры движка (за ночь 2 ложных срабатывания) — когда речь не о
  реальных секретах, формулировать нейтрально.
- **devbot: зелёные команды = только короткие сообщения, префиксы приоритетны** (фикс e2b5c8b):
  зелёная команда матчится ТОЛЬКО на коротком сообщении-команде (≤32 символов, ≤4 слов) и НИКОГДА
  на сообщении со структурированным префиксом (`тз:`/`пк:`/«декомпозируй:») — слово команды в теле
  ТЗ больше не угоняет маршрут.
