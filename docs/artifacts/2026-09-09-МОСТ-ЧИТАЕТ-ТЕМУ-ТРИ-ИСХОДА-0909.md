## 3. ВОПРОС 1 — читает ли серверный обработчик поле темы?

**НЕТ. Ни одной строкой. Ни в Apps Script, ни в питоне VPS.**

### 3.1 Дверь Моста (Apps Script, живой прод @84)

* `bridge_prod/Bridge.js:228` `doPost(e)` — тело разбирается целиком (`:232`
  `JSON.parse(e?.postData?.contents || '{}')`), но по имени берутся РОВНО четыре ключа:
  `body.token` (`:238`), `body.action` (`:242`), `body.origin` и `body.ticket` (`:255–257`,
  токен-замок 4.2). Остальные ключи тела не читает никто — они уходят в обработчик как есть.
* `bridge_prod/Bridge.js:444–445` — `case 'set_needs_approval': setNeedsApproval_(body)`.
  `set_needs_approval` в карте `REDZONE_LOCK` (`:249–257`) **не значится**, поэтому ни билета, ни
  строки боевого лога у этого вызова нет (важно для §5).
* `bridge_prod/BotData.js:398–408` — весь обработчик, дословно четыре чтения payload:
  ```js
  function setNeedsApproval_(payload) {
    var p = payload || {};
    if (p.id == null || String(p.id) === '') return { ok: false, error: 'no_id' };   // :400
    var tab = getBotTab_(BOTDATA.TABS.QUEUE);
    var row = queueFindRow_(tab, p.id);                                              // :402
    if (row < 0) return { ok: false, error: 'not_found' };
    tab.getRange(row, QUEUE_COL.status).setValue('needs_approval');                  // :404
    tab.getRange(row, QUEUE_COL.result).setValue(String(p.what || '').slice(0,5000));// :405
    tab.getRange(row, QUEUE_COL.updated).setValue(new Date());                       // :406
    return { ok: true };
  }
  ```
  Читаются **`p.id` и `p.what`**, и больше ничего. Telegram здесь не вызывается — во всём мосте
  его нет вовсе.
* **Поле негде было бы и сохранить:** `bridge_prod/BotData.js:67–69` `QUEUE_HEADERS` — девять
  колонок `id · created · from · task_text · status · result · approved_by · updated · lane`,
  колонки темы нет. Живая проверка того же дня: снимок очереди (read-only `get_pending`, все
  статусы, обе полосы, **230 рядов**) — ключи ряда ровно
  `['approved_by','created','from','id','lane','result','status','task_text','updated']`.
* **Счёт по всему задеплоенному мосту:** упоминаний поля `topic` (не `topic_id` соседних листов, а
  именно его) в 18 файлах зеркала — **НОЛЬ**.

**Следствие:** поле `topic` умирает на пороге Моста. Оно не читается, не хранится, не
пересылается; ни один следующий читатель его увидеть не может физически.

### 3.2 Тем не менее карточка рождается — и тему ей даёт сервер сам

Карточку владельцу из ряда `needs_approval` делает **devbot внутри процесса `splinter`**
(job `devbot_report`, раз в 45 с; живой след в `splinter.log` за 09:25:57 сегодня). Тема считается
так:

| строка | что делает |
|---|---|
| `devbot.py:2044` | `inbox = inbox_topic()` — единый инбокс |
| `devbot.py:2061` | `_approval_topic = inbox or _item_topic(it)` — **вся развилка темы** |
| `devbot.py:1236–1244` | `_item_topic(it)`: `from ∈ QUEUE_FROMS_PC` → `pc_dev_topic() or DEVBOT_TOPIC`; иначе `DEVBOT_TOPIC` (328) |
| `devbot.py:53–60` | `inbox_topic()` ← env `INBOX_TOPIC_ID`; 0/пусто/мусор = инбокс выключен |
| `devbot.py:42–49` | `pc_dev_topic()` ← env `PC_DEV_TOPIC_ID` (тема 829); 0 = полоса выключена |
| `devbot.py:1628` | второй замок: `_inbox_lock_topic()` — карточка **с кнопкой вердикта** уводится в инбокс, даже если вызывающий посчитал тему иначе |
| `devbot.py:1634` | сама отправка: `message_thread_id = topic` — число, посчитанное выше |

То есть **тема карточки определяется меткой `from` ряда и настройкой инбокса на сервере**, а не
полем вызова. Полоса pc-меток (`devbot.py:197–199` `QUEUE_FROMS_PC`) — `Filipp-pc*`,
`Filipp-pcloc-dec`, `Filipp-revizor`; меток `Filipp-review-claim` и `Filipp-recon-ask` (это и есть
информационные заявки) там **нет**, значит при выключенном инбоксе они получили бы 328, а не 829.
Файл настроек заход не читал (прямой запрет задания) — и ответ от этого не зависит: обе ветви дают
карточку владельцу, разница только в номере темы.

Поиск по всему питону VPS: голого поля `topic`, прочитанного из тела запроса, нет ни одного —
все переменные `topic` в `devbot.py`/`splinter.py` вычисляются на месте.

## 4. ВОПРОС 2 — что происходит, когда поля темы нет или оно пустое

**Исход первый: карточка уходит в тему, которую сервер считает сам.** Не «не доходит» и не «падает».

Доказательство — ветвлением, а не намерением:

1. **Падать нечему.** В `setNeedsApproval_` (`bridge_prod/BotData.js:398–408`) поле `topic` не
   упоминается, значит ни `null`, ни отсутствие ключа не могут дать ни исключения, ни иной ветки.
   Единственные два ранних выхода — `no_id` (`:400`) и `not_found` (`:403`) — про `id`, не про
   тему. Ключ `what` защищён `String(p.what || '')`.
2. **Пропасть нечему.** Ряд получает `status=needs_approval` (`:404`) независимо от содержимого
   тела сверх `id`. Ряд в `needs_approval` — ровно то, что devbot забирает под карточку
   (`devbot.py:2045` `pend = sorted(by["needs_approval"], …)`), и гейт видимости у него теперь не
   список имён, а «чей ряд» (`devbot.py:148` + `_is_our_source`, `:243–249`): любая метка вида
   `Filipp-*` — наша, включая `Filipp-review-claim` и `Filipp-recon-ask`.
3. **Тема берётся из своего источника.** `devbot.py:2061` `_approval_topic = inbox or
   _item_topic(it)` — в этой строке `or` и есть развилка «инбокс задан / не задан»; ни одна из
   ветвей не смотрит в вызов. Затем `devbot.py:1628` второй раз чинит адрес по признаку «есть
   кнопка вердикта».
4. **Ветка молчания есть, но она про другое.** Единственный путь, на котором ряд `needs_approval`
   НЕ станет карточкой, — маршрут находок ревизора по замороженному контуру
   (`devbot.py:2050–2056`, `route["card"] is None` → `continue`), и он выбирается по метке
   `from == QUEUE_FROM_REVIZOR`, а не по теме.

**Прямое следствие для правки полосы ПК от 09.09, ради которого задание и ставилось:**
убрать `topic` из тела вызова — значит не изменить на сервере **ничего**. Ряд по-прежнему
становится `needs_approval`, devbot по-прежнему делает из него карточку с кнопками и по-прежнему
кладёт её в тему, посчитанную на сервере. Информационная заявка мимо инбокса от этого не поедет.

## 5. ВОПРОС 3 — журналы сервера за последние сутки (окно 08.09 09:26 → 09.09 09:26 UTC)

**Сначала честная граница:** отличить «вызов с темой» от «вызова без темы» серверные журналы не
могут **в принципе** — поле не читается (§3.1), в очередь не пишется, и в боевой лог Моста этот
вызов не попадает вовсе (`set_needs_approval` вне `REDZONE_LOCK`, `Bridge.js:249–257`; иных
`logWrite_` в его ветке нет). Поэтому вопрос «были ли вызовы БЕЗ темы» по признаку темы —
**НЕИЗВЕСТНО и будет НЕИЗВЕСТНО всегда**, пока поле не читают. Что журналы отвечают — это были ли
вызовы ЭТОГО ВИДА и что с ними стало.
