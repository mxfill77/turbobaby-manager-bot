## 1. ГДЕ ЗАПИСЫВАЕТСЯ ИСХОД ВНЕШНЕ УПАВШЕГО ЗАХОДА И ЕСТЬ ЛИ ДОСЛОВНЫЙ ТЕКСТ

**ПРЕМИСА ТЗ («не сохраняется — сказать прямо») НЕ ПОДТВЕРДИЛАСЬ. Дословный текст СОХРАНЯЕТСЯ —
в двух местах из трёх. Не сохраняется он ровно там, где его ищут человек и приборы: в журнале.**

Мест записи ровно три, и они не равны:

| место | что туда попадает | дословный ответ внешней системы |
|---|---|---|
| **очередь, поле `result`** | карточка провала `_fail_card` (первая строка stdout + **последние две строки stderr**, cap 600) | **ДА** |
| **артефакт `reports/<дата>/task-<id>.md`** | то же тело, если оно длиннее 600 символов (`devbot.py:1618`) | **ДА** |

Живой факт единственного VPS-отказа окна повода (`orchestrator_daemon.log`, дословно):

```

2026-08-18 16:40:07,159 INFO task-selfheal: id=4 → думатель halt (Провал инфраструктурный
        (API Error: Server error mid-response при exit=1), а не дефект формулировки — переформулировкой )
```

Строка исполнителя несёт **только код возврата**. Дословный ответ появляется в журнале
единственным способом — **ПЕРЕСКАЗОМ ДУМАТЕЛЯ**. Это не частность, а свойство: за всю жизнь
журнала (**21 132 строки, с 19.06**) при **50 ненулевых исходах** `claude -p` слов `API Error`

(совпадения на «529» — куски URL, номер задачи 529 и `RSS 1529МБ`).

А в `result` дословный текст лежит целым:

* задача 4 (полоса vps): `claude -p упал (exit=1): API Error: Server error mid-response. The
  response above may be incomplete.`
* задачи 5, 9, 10 (полоса pc): `claude exit=1: API Error: 529 Overloaded. This is a server-side

**СЛЕДСТВИЕ ДЛЯ О8, названное прямо:** артефакт О8 честно заплатил ценой правила позиции —
«заход #5 из самого повода в череду не попал, его отказ описал только думатель». Разведка

## 2. ОТЛИЧАЕТ ЛИ СИСТЕМА ПЕРЕГРУЗКУ ОТ ИСЧЕРПАНИЯ КРЕДИТОВ

**В записях об исходе захода — НЕТ. Прямо: не отличает, и не может, потому что все виды внешнего
отказа схлопнуты в ОДИН код.** `status_truth.py`:

```python
FAIL_CODES = {
    "approval_timeout": "таймаут подтверждения",
    "heartbeat_timeout": "таймаут сердцебиения",
    "run_timeout":       "таймаут исполнения",
    "model_refusal":     "отказ модели",
    "exec_error":        "ошибка выполнения",
}
_MODEL_NEEDLES = (
    "api error", "overloaded", "oauth", "authenticate", "authentication",
    "rate limit", "usage limit", "credit balance", "server error",
    "model refused", "cannot assist", "не могу выполнить",
)
def classify_exec(out="", err="", rc=None):
    blob = ((str(out or "") + "\n" + str(err or "")).lower())
    if any(n in blob for n in _MODEL_NEEDLES):
        return "model_refusal"
    return UNKNOWN_CODE
```

`credit balance`, `usage limit`, `rate limit` и `overloaded` стоят **в одном кортеже** и дают
**один и тот же** `model_refusal`. Ниже по течению `chain_series.py:320` сводит его ещё грубее —
в «тихий отказ». Кончившиеся деньги и перегрузка сервера неотличимы на всём пути.

**ХУЖЕ ТОГО: код причины у одного и того же отказа РАЗНЫЙ на разных полосах.** В одной очереди,
в одном часе:

```
task-4.md  (vps): [причина=model_refusal · отказ модели]  … API Error: Server error mid-response
task-5.md  (pc):  [причина=exec_error · ошибка выполнения] … API Error: 529 Overloaded …
task-9.md  (pc):  [причина=exec_error · ошибка выполнения] … API Error: 529 Overloaded …
task-10.md (pc):  [причина=exec_error · ошибка выполнения] … API Error: 529 Overloaded …
```

Значит **считать внешние отказы по коду причины нельзя** — полосы кодируют по-разному, и любой
будущий счётчик, построенный на коде, соврёт ровно на межполосном ряду.

**ПРИБОР РАЗЛИЧЕНИЯ КРЕДИТОВ В СИСТЕМЕ ЕСТЬ — И СМОТРИТ НЕ НА ТОТ КАНАЛ. Это главная находка
разведки.** `health.py:368` умеет ровно три исхода — ключ отозван · **«❗кредит платного ключа на
нуле»** · «проба не про кредит», — стоит в проде и гоняется каждые четыре часа. 18.08 он сказал:


## 5. ОДИН НАБЛЮДАЕМЫЙ ПРИЗНАК, КОТОРОГО НЕ ХВАТАЕТ

**Признак: ИСХОД ЗАХОДА ЛЮБОЙ ПОЛОСЫ С ДОСЛОВНЫМ ОТВЕТОМ ВНЕШНЕЙ СИСТЕМЫ — то есть поле `result`
упавшей строки очереди.**

Он не выдуман под будущий прибор и его **не надо добывать: он уже оплачен и уже лежит в руках
наблюдателя**. `expectations_run.py:691`:

```python
def failed_facts():
    """Упавшие строки ОБЕИХ полос → список | None …"""
    r = bc.get_pending("failed", lane="all")
    …
    rows.append({"id": it.get("id"), "lane": it.get("lane"),
                 "task_text": str(it.get("task_text") or "")[:200],
                 "result": str(it.get("result") or "")[:400],
                 "at": expectations.parse_iso(it.get("updated"))})
```

Одним GET, **обе полосы**, с полем `result`. Сегодня этот ответ уходит целиком в
`queue_state.ledger` — в слепок очереди для мозга — и **до судьи (`expectations.verdict`) не
доезжает ни одним полем**. Судья при этом видит из очереди только ОТКРЫТЫЕ строки
(`queue_facts` → `OPEN_STATUSES = new · in_progress · needs_approval · approved`), а упавшая
задача по определению не открыта.

Почему именно этот признак, а не какой-то другой:

* он **один на обе полосы** — снимает и слепоту к полосе VPS, и разнобой кодов причины из §2
  (текст ответа един, код — нет);
* он **дословный** — а это единственное, чем владелец отличит перегрузку от кончившихся денег
  (то же решение принял и О8: не классифицировать, а цитировать);
* он **не стоит нового обращения к миру** — вызов уже делается.

**ДВЕ ЧЕСТНЫЕ ЦЕНЫ, обе измерены:**

1. **Срез 400 символов сегодня отсекает как раз дословную строку.** Измерено на живых отчётах
   (`grep -b`): тело отчёта начинается на байте 4180 (task-4) и 3973 (task-5), а дословный
   `API Error` стоит на 5083 и 5059 — то есть **на 903 и 1086 байте тела**. Кириллица в UTF-8

   влезает лишь **пересказ** думателя (176 байт от начала тела у task-4). Признак есть, обрезка
   его режет.
2. **Вызов условный, а не тактовый:** `failed_facts()` спрашивается, только когда строка ушла из
   открытых либо реестру больше часа (`queue_state.needs_closed`) — ответ дорогой, 301 КБ на
   замере 14.08.

Оба — вопрос настройки уже существующего вызова, а не новой машинерии. **Строить ничего не
предлагаю: признак назван, точки касания названы.**
