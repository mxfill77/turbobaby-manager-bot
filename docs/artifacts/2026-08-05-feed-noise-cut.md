## 2. НЕВЕРНАЯ МЕТКА: SPLINTER — ВНУТРЕННИЙ СЕРВИС

Заметка гласила «рестарт **клиентского бота** · VPS · `systemctl restart splinter`». Клиентский
контур — `userbot_listen` / `moderation_bot` на ПК; splinter обслуживает команду и учёт.

Теперь имя даёт **ЦЕЛЬ команды**:

| цель | класс |
|---|---|
| `splinter` (systemctl restart/start/stop, в т.ч. под `systemd-run`) | `рестарт внутреннего сервиса splinter` |
| `userbot_listen` / `moderation_bot` / `moderbot` (systemctl, `pkill`, запуск питоном) | `стоп/старт/рестарт клиентского бота` |
| демон, `wa-webhook`, health | вне класса вовсе (§4 «не уведомляем») |

**Почему НЕ по метке полосы**, хотя владелец назвал её первой: метка отвечает на вопрос «чья
задача», имя класса — «что тронуто»; это разные вопросы, и второй решается целью. Вывести имя из
полосы было бы вдобавок опасно: у ПК-зеркала `CC_LANE` может быть не выставлен, а
`LANE_DEFAULT` в копии файла — «VPS» (известный остаток), и настоящий клиентский бот назвался бы
внутренним. Цели двух семейств не пересекаются — имя по цели верно на любой полосе, и метка
полосы рядом остаётся в каждой заметке, как была.

## 3. ДВОЙНОЙ ОТЧЁТ О ЗАДАЧЕ — ОДНО СООБЩЕНИЕ

**Как было.** Вердикт куратора живёт в очереди synthetic-задачей `[куратор задача N]`: демон
кладёт её, тут же закрывает `done`, а devbot рапортует её как обычную задачу — вторым сообщением
следом за итогом. Плюс иногда третьим — анонсом «🔄 в работе» по ней же (карточка успевала
попасть в журнал взятий).

**Замер по журналам (28.07–05.08, 9 суток):** 613 сообщений devbot в 328, из них **88 (14 %)** —
кураторские карточки (66) и анонсы «в работе» по ним (22).

**Как стало.** Вердикт — СТРОКА внутри карточки задачи:

```
✅ Задача 318 — done
<суть отчёта>
🧭 Куратор: цель не закрыта — продолжение: задача 331
⏳ Работа продолжается: 1 (🎭 vps 1) (331)
```

* вердикт УСПЕЛ до первого рапорта (частый случай: думатель ~10 с, тик 45 с) — строка едет в
  самой карточке;
* вердикт пришёл позже — строка дописывается ПРАВКОЙ того же сообщения (правка не сообщение);
* цель закрыта без замечаний — куратор молчит, как молчал (`verdict=closed` карточки не рождает);
* анонс «🔄 в работе» о карточке-маркере не шлётся вовсе.

**FAIL-SAFE — главное свойство правила:** пометка «вклеено» ставится ТОЛЬКО по факту доставки, а
вердикт, который в строку не влезает, в неё и не ужимается. `_curator_line` возвращает `None`
для тел со сбоями («НЕ поставлено» — ТЗ не встало по бюджету/дедупу/enqueue; «сводная карточка
владельцу НЕ встала»), и такая карточка уходит отдельным сообщением ЦЕЛИКОМ, как раньше. Молча
не теряется ни одного слова куратора.

**Замер после (тот же корпус):** 613 → **531** сообщения (68.1 → **59.0** в сутки), гаснет 82
(13 %). Из 74 кураторских карточек журнала вклеиваемы 67; шесть остаются отдельным сообщением по
fail-safe — ровно те, где куратору есть что сказать сверх строки. **Это верхняя оценка экономии:**
частичный отказ постановки («поставлено 1 из 2») в журнале демона не виден, а такие карточки
правило не гасит, значит реальная экономия чуть меньше расчётной, но не больше.

### 3.1 Побочная находка того же места: 405 правок, которые ничего не меняли

Плашка «🧭 Куратор оценивает итог — вердикт через ~10с» снималась по таймауту вызовом
`_build_banner` — той же функции, которая эту плашку и ставит. Условие внутри не изменилось →
текст получался ТОТ ЖЕ → Telegram отвечал «Message is not modified». В живом журнале таких
падений **405**, и все карточки закрытых без замечаний целей навсегда остались с надписью
«вердикт через ~10 с», хотя вердикта уже не будет. Теперь у фолбэка есть `curator_wait=False`:
плашка показывает состояние очереди — оно истинно и когда куратор промолчал, и когда он умер.
Различить эти два случая нечем, поэтому плашка не заявляет ни одного из них.

### 3.2 Правка не имеет права обеднить сообщение

Раз сообщение теперь ОДНО, оно обязано остаться полным. При дописывании вердикта кнопки
восстанавливаются те же, что стояли: у урезанного отчёта — «📄 отчёт» (у `failed` она вообще
единственная). До правки edit ставил `_kb_done(qid)` без флага и молча снимал кнопку полного
отчёта, появившуюся 05.08 вместе с дайджестом.

### 3.3 Память «вклеено» живёт минуты, а не вечно

Пометка `_curator_glued` — словарь с TTL 3600 с (тик — 45 с). Долгая память здесь опасна: при
ПЕРЕСОЗДАНИИ очереди номера начинаются заново (живой случай 28.07), и старый ключ погасил бы
чужую карточку.

## 5. ОСТАТКИ, НАЗВАННЫЕ ЧЕСТНО

* **Зеркало ПК-полосы не сделано.** Точки касания: таблица `_CLASSES` и предикат `_bot_ctl` в
  копии ленты на ПК (там же обязан смениться `LANE_DEFAULT` → «ПК» либо ставиться `CC_LANE`);
  для отчёта — свой рапорт pc-полосы, куратор там не живёт, поэтому вклейка вердикта ПК не
  касается вовсе.
* **Правка devbot живёт в git, но не в проде:** splinter держит старый код в памяти процесса, а
  рестарт клиентского контура в этом заходе запрещён владельцем. Класс «фикс в git ≠ фикс в
  проде» — сокращение сообщений в 328 заработает только после рестарта splinter. Правка ленты,
  наоборот, живая сразу: `posttool_feed.py` — отдельный подпроцесс хука на каждый вызов
  инструмента, ни демон, ни splinter его не импортируют (проверено grep'ом по репозиторию).
* **Частичный отказ постановки** («поставлено 1 из 2») в журнале демона не виден — доля
  fail-safe-карточек измерена по нижней границе (6 из 74).
* **ПК-формы клиентского бота живым корпусом VPS по-прежнему не подтверждены** (остаток шага 2):
  на этой полосе таких команд нет вовсе, форма взята из карты процессов ПК.
