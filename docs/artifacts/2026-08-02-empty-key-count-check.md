# Сверка числа: «4 строки с пустым ключом» против «0 из 85». Прав счётчик; четыре — это не строки

**Дата:** 02.08.2026 · **Репо:** turbobaby-manager-bot · **Режим:** read-only, код не правился
**Предмет:** `docs/artifacts/2026-08-02-enqueue-dedup.md` §5 против счёта задачи 209
(`docs/artifacts/2026-08-02-event-key-required.md` §5)
**Разведка:** `_scratch_cur209/recon209_keys.py`, `recon209_blind.py`, `recon209_final.py`

## Итог одной строкой

**Оба числа верны — они об разном, а посылка ТЗ ложна.** Счёт «0 пустых из 85» устоял под
независимым пересчётом. Четыре метки из §5 — **не строки листа**: это ровно четыре момента
**пересылки** write-POST записи события, у всех четырёх ключ **непустой**. Разд. 5 помечен
**частично опровергнутым**: список моментов подтверждён, объяснение причины — нет.

## 1. Счётчик 209 пересчитан независимо: 85/0 подтверждено

Оригинал (`_scratch_evkey_0802a/recon_empty_keys.py`) якорит ключ на СОСЕДНЕЕ поле
(`msg_id=(.*?) info_works=` и `msg_id=(.*?) add_event `) — если формат строки поедет, счётчик
промолчит. Проверено свободным разбором (якорь только на маркер строки, ключ — до следующего
поля `\w+=`):

| | свободный разбор | regex задачи 209 |
|---|---|---|
| обычное событие | 76 | 76 |
| инфо-работа | 9 | 9 |
| **итого** | **85** | **85** |

Расхождений — **0 строк**. Пустых ключей — **0**. Формы ключей в окне: `-1002751134848:*` (76),
`info:*` (9).

**Окно покрыто логом непрерывно** (это условие того, что «0» значит «не было», а не «не видел»):
`splinter.log` един, без ротации, 01.06 19:53 – 02.08 20:30; по суткам окна 26.07→02.08 —
648 / 4204 / 4187 / 4178 / 4096 / 4505 / 5144 / 4569 строк, дыр нет.

**По всему логу (01.06–02.08): 417 строк печатают поле ключа, пустых значений — 0.**

## 2. Побочная находка метода: «поля нет» ≠ «ключ пуст»

Свободный разбор поднял 18 строк 09–10.06 и 29.06 без поля ключа — и первый проход посчитал их
пустыми. **Это ложные срабатывания моего же детектора:** тогда строка лога поля не печатала, а код
слал ключ `{msg_id_base}:w{i}` — непустой (диф `2807718` от 29.06, он же завёл контентный `info:…`
и поле в строку). Внутри окна 7 суток таких строк **0**, поэтому счёт 209 они не задевают.

Класс (в дополнение к правилу 8): **счётчик по логу обязан различать «значение пусто» и «поля не
было» — формат строки лога меняется во времени так же, как формат ячейки листа.** Требование поля
в регексе (как у 209) от ложного нуля защищает, но тихо выкидывает старые строки из знаменателя.

## 3. Знаменатель — вот где счёт слаб, и слабость измерена

Артефакт 209 честно оговорил, что ключ печатают 2 пути из 8. Размер слепой зоны теперь назван
числом: в ТОМ ЖЕ окне строка диспетчера (`Splinter [mode] …`, печатается на каждое входящее)
даёт **delivery 166 сообщений, из них 142 с текстом → запись** (голое фото выходит без записи) и
**attendance 35 → пишет каждое**. Итого **~177 записей события прошли без свидетельства ключа**.

**Счётчик видел ≈32 % (85 из ~262).** Ключ у этих 177 непустой по построению
(`f"{chat_id}:{msg.message_id}"`, `splinter.py:6892/6909`), но лог этого не свидетельствует —
поэтому «0» остаётся «ноль среди свидетельствуемых», как и было сказано, просто теперь известно,
насколько это меньше целого.

## 4. Откуда взялись «четыре»: это пересылки, а не строки

Разбор окрестностей четырёх меток даёт однозначный ответ — они **дословно совпадают с моментами
пересылки** записи события (`Bridge add_event: unauthorized (токен потерян на редиректе?) —
пересылаю запрос с токеном заново`):

| метка §5 | что это на самом деле | ключ |
|---|---|---|
| 01.08 07:56:02 | пересылка; ветка `[delivery]` (сообщения 07:54–07:56) | `<чат>:<id>` по построению |
| 01.08 07:58:01 | пересылка; 07:58:51 → `error=request_failed` | **непустой, напечатан:** `-1002751134848:11091` |
| 01.08 10:48:09 | пересылка; ветка `[attendance]` (сообщение 10:47:27) | `<чат>:<id>` по построению |
| 02.08 04:11:30 | пересылка; 04:11:48 → `ok=True duplicate=True` | **непустой, напечатан:** `-1002751134848:11117` |

Пересылок записи события в окне ровно **4**, за весь лог — **9**. Отсюда и число «четыре»: это
счёт ПЕРЕСЫЛОК (класс, закрытый `d78d5fa`), а не счёт анонимных строк листа. Метка 02.08 04:11 —
прямое доказательство работы ключа: пересылка схлопнута дедупом (`duplicate=True`).

## 5. Вердикт по разд. 5 `2026-08-02-enqueue-dedup.md`

**ПОДТВЕРЖДЕНО:** неопределённый случай действительно среди этих четырёх моментов — других
подозрительных моментов записи события в окне нет (пересылок ровно 4).

**ОПРОВЕРГНУТО:** «неопределённым может остаться **только** событие с ПУСТЫМ `msg_id`». Живой
контрпример — 01.08 07:58:51: ключ непустой, а исход неизвестен (`request_failed` на пересылке).
Разд. 5 склеил два разных вопроса:

* **«дубль ли это?»** — непустой ключ решает: двух строк с одним ключом `addEvent` не создаст
  (`botMsgExists_`, `BotData.js:509`);
* **«прошла ли запись вообще?»** — ключ не решает НИЧЕГО, и решить это клиентом нельзя:
  лист с колонкой ключа read-only не читается. Проверено **живым** вызовом, не только кодом:
  ответ чтения истории байка несёт `recorded_at / msg_date / event_type / mileage / notes` —
  колонки ключа в ответе **нет** (`readEvents`, `BotData.js:591-614`).

Значит неопределённость там — от **неизвестного исхода пересылки**, а не от анонимной строки.
(Мелкая честность о самой проверке: автопроверка «есть ли в ответе поле с `msg`» дала истину на
`msg_date` — вывод сделан по перечню полей, а не по этому флагу.)

**ПОСЫЛКА ТЗ ЛОЖНА ДВАЖДЫ:** §5 не называл строк листа (он прямо оговорил, что лист с VPS не
перечисляется) и не утверждал пустоту как факт — он вывел её исключением. Это второе независимое
подтверждение находки А в `2026-08-02-event-key-required.md` §3, теперь с корнем числа «4»,
которого там не было.

## 6. Что из этого следует

1. Правка `73d2072` (запрет пустого ключа на входе) остаётся оправданной — но как **запрет
   класса**, а не как починка наблюдавшихся четырёх случаев: чинить там было нечего.
2. Неопределённый случай **не закрыт и клиентом не закрывается**. Закрыть можно двумя ходами, оба
   прежние: сверка ключа сервер-сайд в `enqueueTask_`/`addEvent` + `clasp redeploy` (**красная
   зона, деплой владельцем**) либо глаз владельца в листе.
3. Дешёвый ход, снимающий слепые 68 %: одна диаг-строка с ключом на каждый из шести молчащих путей
   записи (остаток 3 артефакта `event-key-required`). Тогда счёт по логу перестанет быть счётом
   трети.
