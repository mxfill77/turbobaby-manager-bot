# Запись события требует ключ сообщения + две находки против исходной посылки

**Дата:** 02.08.2026 · **Репо:** turbobaby-manager-bot · **Файлы:** `bridge_client.py`,
`tests/test_event_key.py`, `tests/test_post_receipt_no_resend.py`
**Коммиты:** `73d2072` (правка+тест), `7dabc82` (фикстура расписки)
**Основание:** `docs/artifacts/2026-08-02-enqueue-dedup.md` §5. Повтор задачи 208 (закрыта отказом).

## 1. Правка

`bridge_client.add_event`: ключ сообщения (`msg_id`) обязателен. Пусто / `None` / одни пробелы →
запись НЕ уходит на мост, наружу `{ok:False, error:"no_msg_id"}`, а суть события
(группа/байк/тип/пробег/заметка) уходит в журнал — **отказ не молчаливый**: «не прошло» обязано
быть отличимо от «прошло», иначе событие теряется бесследно.

**Почему запрет, а не «дедуп выключен».** `botMsgExists_` на пустом ключе возвращает ложь
(`if (!msgId) return false`, `BotData.js:449-450`) — строка ложится в лист сразу без двух вещей:
без защиты от дубля и без свидетеля. Её нельзя ни сверить, ни отозвать: `delete_event` тоже
работает ТОЛЬКО по точному ключу и без него отказывает (`BotData.js:549`). Тот же принцип теперь
стоит на входе, а не только на удалении.

**Направление отказа ОБРАТНОЕ постановке — намеренно.** У `enqueue_task` (667d314) пустой ключ =
«дедупа нет, поведение прежнее» (fail-open: потерять задачу владельца хуже, чем продублировать).
Здесь fail-closed: анонимная строка в живом листе хуже ненаписанной, потому что она необратима по
ключу и навсегда портит сверку. Форма взята от постановки, знак — от предмета.

## 2. Законные записи без ключа: их НЕТ, и заменять свидетеля не нужно

Вопрос ТЗ — есть ли автоматические записи не от сообщения владельца. **Есть, и все они уже несут
синтетический КОНТЕНТНЫЙ ключ** (разбор `ast` всех 8 живых вызовов в `splinter.py`):

| путь | ключ | откуда |
|---|---|---|
| инфо-работа | `info:<номер>:<работа>:<км>` | `splinter:2062` |
| аудит одометра | `odo_audit:<чат>:<тема>:<км>` | `splinter:2849` |
| ТО фаза 2 | `sp:<чат>:<тема>:<вид>:<км>` | `splinter:5861` |
| событие сообщения, intake, delivery, attendance | `<чат>:<id сообщения>` | `6135/6081/6892/6909` |
| перезапись при откате км | `**kw` — ключ прежней записи | `splinter:2227` |

Контентный ключ **и есть** замена свидетеля для автоматики: он строится из СОДЕРЖАНИЯ события, и
повтор того же факта даёт тот же ключ (мост схлопывает). Ломать нечего — ни один живой путь не
писал без ключа. Новому автоматическому писателю брать эту же форму; страж в тесте (см. §5)
красит любой новый вызов, забывший ключ.

## 3. Находка А: посылка ТЗ живым фактом НЕ подтверждается

ТЗ утверждает, что четыре строки листа (01.08 07:56:02 / 07:58:01 / 10:48:09, 02.08 04:11:30)
записаны с пустым ключом. Артефакт §5 этого НЕ утверждал — он **вывел исключением** («неопределённый
может остаться только событие с пустым msg_id»), прямо оговорив, что лист с VPS не перечисляется.
ТЗ прочитало вывод как факт и умножило один случай на четыре.

Клиентский свидетель (`splinter.log`, UTC) в эти моменты показывает **непустые** ключи:

* 01.08 07:58:51 — `ok=False error=request_failed msg_id=-1002751134848:11091`, HTTP 302
  → это класс **пересылки write-POST**, закрытый `d78d5fa`, а не пустой ключ;
* 02.08 04:11:48 — `ok=True duplicate=True msg_id=-1002751134848:11117` — ключ СРАБОТАЛ,
  дубль схлопнут;
* 01.08 07:56 — ветка `[delivery]`, 01.08 10:47–10:48 — ветка `[attendance]`; обе пишут
  `<чат>:<id сообщения>` по построению.

Правка всё равно нужна и сделана — но как **запрет класса на входе**, а не как починка
наблюдавшихся четырёх строк. Утверждать, что те строки анонимны, оснований нет.

## 4. Находка Б: чем проба задачи 208 обошла изоляцию `a739ee9`

**Изоляцию она не обходила — та просто не применилась.** Признак `a739ee9` отвечает на вопрос
«идёт ли ТЕСТ-ПРОГОН»: `is_test_run` (четыре env-имени), env-префикс в тексте команды, либо
`_is_test_script`. Проба 208 — read-only разбор лога, запущенный ВНУТРИ живой headless-задачи
(`venv/bin/python3 _scratch_evkey_0802a/recon_empty_keys.py`): демон снимает тест-флаги с окружения
намеренно, имя файла не `test_*`, env-префикса в команде не было → ни одного признака → оба канала
владельца боевые.

**Красноту дал СТРОКОВЫЙ ЛИТЕРАЛ.** В теле пробы стояла строка `"add_transaction" in line` —
шаблон для грепа по логу. `_py_code_view` намеренно оставляет строковые константы в коде-виде
(`pretool_guard.py:212-213`, асимметрия «корня А»: имя операции в строке МОЖЕТ быть действием).
Дальше денежный класс не гасится объектным гейтом никогда (`_ALWAYS_CARD` → `card_gate` возвращает
истину даже с пустым объектом, `pretool_guard.py:438`) — отсюда карточка «проводка ДЕНЕГ в кассу»
с ПУСТЫМИ объектом и числом. Пустота объекта — не сбой карточки, а её честный вид: вызова-то нет.

Складывается класс: **read-only разведка, которой нужно грепать имя пишущей операции, обязана либо
объявить себя пробой env-префиксом, либо не называть операцию литералом.** Второе здесь достижимо
и дешевле — в этой задаче счёт снят грепом по СОСЕДНИМ полям строки (`info_works=`,
`инфо-работа в историю`), имя операции не набиралось вовсе, и гард не был задет ни разу.

Предупреждение на будущее: пометка «проба» прав НЕ даёт (решение deny/ask не меняется), поэтому
для скрипта, который гард судит как пишущий, префикс спасает от карточки владельцу, но НЕ спасает
от авто-отказа в headless — читающая проба должна быть чистой по литералам.

## 5. Счёт (без правки, ответ на вопрос ТЗ)

**Событий с пустым ключом за 7 суток (26.07 20:11 – 02.08 20:11 UTC): 0.**

Из 85 записей события, которые свидетельствуются логом (76 диаг-строк обычного события + 9
инфо-работ), пустых ключей — ноль. По всему логу (01.06–02.08, 388 диаг-строк) — тоже ноль.

**Предел числа назван честно:** ключ печатают только 2 из 8 путей записи; `intake`, `delivery`,
`attendance`, `odo_audit`, ТО фазы 2 и перезапись отката в лог ключ не пишут. Поэтому 0 — это
«ноль среди свидетельствуемых», а не «ноль в листе». Лист «события» read-only с VPS не
перечисляется (`readEvents` фильтрует по номеру байка, выбрасывает строки без `notes`/`mileage`
и `msg_id` вообще не отдаёт, `BotData.js:591-614`). Структурный аргумент сильнее счёта: все 8
вызовов несут ключ по построению (§2), а теперь ещё и не могут его не нести (§1).

## 7. Остатки

1. **Зеркало на мосту.** Проверка КЛИЕНТСКАЯ; сам `addEvent` пустой ключ примет
   (`p.msg_id || ''` → `appendRow`). Зеркало — `if (!msgId) return {ok:false, error:'no_msg_id'}`
   в `BotData.js:505` (форма уже есть рядом: `deleteEvents` отказывает `no_key`, строка 549)
   + `clasp redeploy` — **красная зона, деплой владельцем**. Сегодня вход закрыт полностью:
   живой писатель событий один — splinter.
2. **Четыре строки листа.** Чтобы закрыть вопрос §3 фактом, нужен глаз владельца в листе либо
   отдельное read-only действие «строки за интервал» (с `msg_id`) — `read_events` для этого не
   годится по §5.
3. **Ключ в лог у остальных 6 путей.** Сегодня 6 из 8 путей записи не печатают ключ — счёт
   §5 поэтому неполон по построению. Дешёвая правка: одна диаг-строка на путь.
4. **Зеркало ПК-полосы не проверено** (правило «класс-фикс на обе полосы»): если в ПК-репо есть
   свой писатель событий, у него тот же вопрос. Точка касания — клиент `bridge_http` (метод
   записи события), зеркало `bridge_client.add_event`.
