# Порог веса серии: число из замера и замок под ним (11.08.2026)

**Задача.** Поставить порог веса — последний кусок счётчика серии. Рамка §8г: «серию можно
удлинить, ослабив гейт, поэтому длина без веса не засчитывается». Порог ставится ПОСЛЕ замера
доли цепочек, изменивших операционное состояние.

**Корпус.** Снимок очереди 11.08.2026 10:41 UTC — **492 записи → 309 цепочек** (307 закрытых,
2 открытые; vps 154 · pc 155), окно 28.07 10:18 — 11.08 10:41. Факты мира: `origin/main` (492
коммита), журнал systemd (50 стартов юнитов), 206 окон METRICS демона. Всё read-only: очередь,
таблицы и процессы не тронуты; каталог захода — `_scratch_weight_0811/` (не удалён).

## 1. Прибор мерил ДИСЦИПЛИНУ НАЗЫВАНИЯ — и это не предупреждение, а живой факт

Замер 11.08 (`2026-08-11-chain-breaks-weekly-comparability.md` §4) оговорил: рост веса
41.0 → 64.3 → 85.7 % частично объясняется тем, что отчёты стали чаще называть хеш (56 % → 79 %
при росте коммитов на цепочку всего 0.61 → 0.71). Проверка прибора показала **хуже оговорки**.

Вес по коммиту засчитывался так: найти в ТЕКСТЕ терминала хеш → сверить с `origin/main` → если
метка коммита попала в окно ОЧЕРЕДИ записи (от постановки до терминала), зачесть. Окно очереди
шире окна ИСПОЛНЕНИЯ, и в зазоре живёт ЧУЖАЯ работа:

| цепочка | зачтено по хешу | чьи это коммиты на самом деле |
|---|---|---|
| 101 | 1c23895, bbbe458, e4f3999, ffa2e3b | 98, 93, 97, 19 |
| 102 | 1c23895, bbbe458, e4f3999 | 98, 93, 97 |
| 112 / 113 | 9da54b8, fc07efa | 108, 103 |
| 235 | ada5c4e | 234 |
| **361** | **девять хешей** (05c110b, 20ebbc1, 40c8425, 53ce1a9, 9906598, 9da54b8, a77c14e, af55ac7, baf1c60) | 319, 262, 318, 228, 320, 108, 59, 182, 360 |

**Из 68 цепочек, зачтённых по хешу, ШЕСТЬ не имели ни одного своего коммита** — им зачли работу
соседей, процитированную в отчёте. Обратная ошибка ровно того же размера: **шесть цепочек
(19, 56, 58, 59, 69, 130) сделали коммит и не назвали хеш** — их работа не засчитана.

**Замок.** Вес приписывается ОКНОМ ИСПОЛНЕНИЯ (METRICS демона, `mode=prod` — тот же источник,
которым уже приписываются перезапуски), текст отчёта не читается ВООБЩЕ; `_SHA` из
`chain_series_report` снята, у `_series_commits` демона аргумента с отчётом больше нет.
Хвоста у окна нет намеренно (в отличие от рестартов): коммит рождается внутри исполнения по
построению, а хвост отдал бы цепочке чужую соседнюю работу. Проверено: **ни один коммит корпуса
не попал в окна двух цепочек сразу** (полоса vps одно-воркерная).

Прогон ДО/ПОСЛЕ на дословных случаях (дерево `5257df6` через `git worktree`):

| случай | ДО правки | ПОСЛЕ |
|---|---|---|
| цитата чужого хеша (361), коммит в зазоре окон | **вес ДА** `['40c8425']` | вес нет |
| работа в окне, хеша в отчёте нет (130) | **вес НЕТ** | вес да |

Сдвиг числа при этом мал — прибор чинился ради честности, а не ради цифры: вес по наблюдаемым
**54.6 % → 52.6 %** (83 → 80 из 152), по неделям 41.0/64.3/61.9 → **39.3/61.4/61.9**.

## 2. На какой единице мерить

Порог применяется к ИДУЩЕЙ серии, то есть к отрезку **чистых цепочек подряд**. Прежний порог
0.25 выведен 10.08 по другой единице — ряду НАБЛЮДАЕМЫХ цепочек, из которого выброшено всё
невидимое; такой ряд плотнее живого, и дно у него ниже (23.3 %). Здесь мерилось то, что порог
реально встречает: **окно в `SERIES_TARGET` = 30 чистых цепочек подряд, 155 окон**.

Наблюдаемых внутри такого окна: **min 0 · p10 2 · медиана 17 · p90 23 · max 26**.

| знаменатель (наблюдаемых в окне) | достижим | дно доли веса |
|---|---|---|
| ≥10 | 118 из 155 (**76 %**) | **35.0 %** |
| ≥15 | 94 (61 %) | 35.0 % |
| ≥20 | 47 (30 %) | 35.0 % |
| ≥24 | 15 (**10 %**) | 54.2 % |
| без ограничения | 152 | 0.0 % (7 окон, все со знаменателем 1–3) |

Отсюда **знаменатель ≥ 10**: дно СТАБИЛЬНО (35.0 %) при ≥10, ≥15 и ≥20 и обваливается до нуля
ниже десяти; при этом ≥10 достижим в трёх четвертях окон, а ≥24 — в одном из десяти, то есть
порог, требующий почти полной наблюдаемости, молчал бы почти всегда.

Распределение судимых окон (знаменатель ≥10, 118 окон): **min 35.0 % · медиана 57.9 % · max
75.0 %**.

## 3. Число: 0.30, и вот арифметика

Дно — величина **дискретная**: оно шагает на одну цепочку своего окна. Худшее окно корпуса —
**7 весомых из 20 наблюдаемых** (цепочки 9…102) = 35.0 %, шаг одной цепочки там **5.0 п.п.**

> **ПОРОГ = живое дно − ОДНА цепочка того же окна = 35.0 − 5.0 = 30.0 %.**

| порог | окон живой работы ниже него | запас до дна |
|---|---|---|
| 25 % | 0 из 118 | +10.0 п.п. = **+2.00** цепочки |
| **30 %** | **0 из 118** | **+5.0 п.п. = +1.00 цепочки** |
| 33 % (1/3) | 0 из 118 | +1.7 п.п. = +0.33 цепочки |
| 35 % | 0 из 118 | 0.0 — порог совпал с дном |
| 40 % | **1 из 118** | −5.0 п.п. = −1.00 цепочки |

**Почему не выше.** 40 % отказало бы живому окну. 35 % стоит ровно на дне. 33 % оставляет треть
цепочки: одна невезучая цепочка в худшем окне — и честная работа объявлена подлогом.

**Почему не ниже.** 25 % на корпусе ведут себя ТОЧНО так же (ниже 25 % и ниже 30 % — по 0 окон
из 118), то есть лишние 5 п.п. зазора не покупают ни одной ошибки меньше; они лишь ослабляют
замок, придвигая порог к тому, ради чего он заведён, — к набитой длине. Прежние 0.25 к тому же
оставляли под собой ОДНО окно из 109 (дно 23.3 % при пороге 25 %); новый порог строже и при этом
не оставляет под собой ни одного.

## 4. Вторая оговорка замера: слепоту порогом не карают

Вес полосы pc не наблюдаем по построению — она коммитит в чужой репозиторий (0 из 155 pc-цепочек
против 80 из 152 vps). Раньше зачётность была БУЛЕВОЙ, и серия без единой наблюдаемой цепочки
получала «не зачётная» — то есть наказание за чужой репозиторий. Теперь исходов **три**:

* **да** — длина ≥ 30 И доля ≥ 30 % при знаменателе ≥ 10;
* **нет** — длины нет (длина наблюдаема ВСЕГДА, это факт) ЛИБО доля ниже порога на достаточной почве;
* **неизвестно** — наблюдаемых цепочек меньше 10: судить не на чем, и это НЕ незачёт.

Ровно так выглядит нынешний рекорд: **17 цепочек 164…180 — полоса pc целиком, наблюдаемых 0**.
Его зачётность не опровергнута, она **не судима**.

## 6. Границы и остатки

* `pretool_guard.py` не изменён ни на строку; сорта вмешательства, `SERIES_TARGET`, критерий
  выхода из фазы, дежурный, куратор и лента не тронуты. Клиентского контура заход не касался,
  в рабочие таблицы не писал, ничего не удалял; `_scratch_series_iso_0810/` и
  `turbobaby-bridge-gs/` не трогались.
* **Приписка коммита условна ровно настолько же, насколько приписка рестарта.** Коммит владельца
  из Termux, сделанный ВНУТРИ окна исполнения headless-задачи, будет засчитан ей. Разделить их
  нечем: `git` пишет обоим одного автора. Обратная ошибка исключена по построению — вне окон
  осталось 397 коммитов из 492 (80.7 %), и ни один из них никому не приписан.
* **Коммит, не доехавший до `origin/main` к моменту терминала, живым счётом не увидится**
  (реплей увидит позже). Направление ошибки — в занижение веса, как и договорено.
* Метка коммита читается как `%cI` + `chain_series.stamp` — то же, что делает реплей с 10.08.
  Коммит, сделанный в НЕ-UTC зоне, обе стороны прочтут одинаково неверно; на этой машине таких
  нет (сервер в UTC).
* **Зеркала ПК-полосы нет** — точки касания: приписка коммита окном, три исхода зачётности,
  оба числа порога.
* **Класс «фикс в git ≠ фикс в проде» ДЕЙСТВУЕТ** для живого счёта: `_series_commits` живёт в
  памяти демона, доставка = перезапуск. Реплей (`chain_series_report.py`) и решение
  (`chain_series.py`) читаются с диска и живут сразу.
* Порог держится на ОДНОМ худшем окне (7 из 20). Появится окно хуже — дно опустится, и число
  придётся пересчитать тем же способом: `chain_series_report.py` печатает строку «ПОРОГ ПРОТИВ
  ЖИВОЙ РАБОТЫ» с числом окон под порогом на каждом прогоне, так что момент будет виден.

**Тесты.** `tests/test_chain_series_weight.py` — **33/33** (голдены на дословных случаях 361 и
130; до правки сьют не стартует вовсе: у дерева `5257df6` нет самого понятия знаменателя —
`AttributeError: WEIGHT_MIN_KNOWN` после первой же красной проверки числа порога). Догнаны по
изменившемуся словарю `test_chain_series.py` (99/99), `test_chain_cards.py` (39/39),
`test_orchestrator_other.py` (15/15 — читающий `git log` исключён из запрета хардкод-команд по
словарю `prod_drift.GIT_READ`, а не по своему списку).
