## 1. МЕСТА, ГДЕ ДВА СМЫСЛА СЛИТЫ В ОДИН БИТ

### 1.1 Серверная полоса — дословно

**(а) Одна классификация решает обе величины.** `pretool_guard.py:643-652`:

```python
def decision(kind, hit, reason):
    if kind in ("green", "ambiguous"):
        return None
    return {"hookSpecificOutput": {
        "hookEventName": "PreToolUse",
        "permissionDecision": "ask" if can_approve(kind, hit) else "deny",
        "permissionDecisionReason": reason}}
```

`kind` — единственный вход. Из него следует и власть (`ask`/`deny`/пропуск), и наличие адресата.
Соседняя функция говорит это прямым текстом (`:637-640`):

```python
def can_approve(kind, hit=""):
    """False = ЖЁСТКИЙ БЛОК: ни карточки владельцу, ни «да» — обойти нельзя (deny хука).
    Единственный источник правды: по нему же main() решает, слать ли карточку/конверт."""
```

«Единственный источник правды» для ДВУХ разных вопросов — это и есть склейка, названная в коде.

**(б) Ветка «пропустить» выходит РАНЬШЕ, чем в программе появляется адресат.** `main:1806-1807`:

```python
    if kind in ("green", "ambiguous"):
        _defer()                  # читающий python / не-python / ambiguous (в3) → штатные allow/ask/deny
```

`_defer` — это `sys.exit(0)` без единой строки stdout (`:633-634`). Ни `_push`, ни
`_guard_write_marker` ниже по коду не достижимы. **Пропуск ⇒ молчание по построению**, а не по
решению: клетка «пропустить и сказать» не «редко используется», её физически нет.

**(в) Карточка и отказ — один и тот же объект.** `main:1843-1851`:

```python
    _guard_write_marker(tid, hit, card, blocktype=blocktype)
    _push(card)
    _ask(_probe_intercept(card, tid) if probe else card)
```

`_ask(reason)` = `_emit(decision("red", "", reason))` (`:661-662`), то есть **текст карточки
подставляется как ПРИЧИНА отказа**. Уведомление не «сопровождает» блок — оно им является.

**(г) Единственное место, где величины разведены, разводит их ТОЛЬКО в одну сторону.**
`main:1837-1842` + `card_gate:951-970`:

```python
    obj, num = card_min(hit, blob)
    if not card_gate(hit, obj, num):
        why = "объект=%s, число=%s" % (obj or "—", num or "—")
        _guard_log("card_skipped", cmd, hit + ": " + why)
        _ask("🔴 КРАСНОЕ (%s) — карточки нет: %s. Владельцу не отправлена, факт записан в журнал "
             "гарда; решай по самой команде." % (hit, why))
```

Комментарий над веткой (`:1831-1836`) формулирует асимметрию буквально: «Гард при этом НЕ слабеет:
решение остаётся ask… молчим только в каналах владельца». Значит система УМЕЕТ снять внимание,
сохранив власть — `(block, silent)`, — и не умеет обратного, `(pass, notify)`.

**(д) Жёсткий блок — та же асимметрия на максимуме власти.** `main:1808-1811` и `_BLOCK_TEXT`
(`:579-587`): «Карточка владельцу НЕ шлётся, approve НЕВОЗМОЖЕН». Самый опасный класс операций даёт
владельцу РОВНО НОЛЬ сигнала.

**(е) На уровне демона склейка физическая: маркер = убийство исполнителя.**
`orchestrator_daemon.py:503-515`:

```python
def _guard_monitor_loop(tid, proc, stop_event, kill_event, card_holder):
    """Фон-поток: каждые 2с проверяем маркер. Нашли → terminate claude → kill_event."""
    path = _guard_marker_path(tid)
    while not stop_event.wait(2.0):
        if os.path.exists(path):
            data = _guard_marker_read(tid)
            card_holder.append(data or {})
            try:
                proc.terminate()
```

Файл маркера — ЕДИНСТВЕННЫЙ канал гарда к владельцу в headless (второй, `_push`, идёт мимо задачи).
И он же — команда «убей работу». Сказать владельцу, не остановив задачу, нечем: канала для этого
не существует.

### 1.3 ОТКРЫТЫЙ КЛАСС: одно имя, противоположная власть

`card_gate` — функция, специально сведённая к одному правилу на обе полосы (коммит `cb4e3e2`,
29.07, «одно правило карточки на обе полосы»). Свело она **внимание**. **Власть при этом
разъехалась:**

* сервер, `main:1838-1842`: `card_gate=False` → `_ask(...)` → **команда НЕ исполняется**;
* ПК, по замеру задачи 185: «`card_gate:3495` при пустом объекте отдаёт `journal`, и `main` выходит
  `sys.exit(0)` — **операция исполняется**».

Одинаковое имя, одинаковый текст правила, противоположный исход для операции. Именно потому, что
величина одна, а смыслов два: сводили видимый (внимание), а вместе с ним молча развели невидимый
(власть). Проверить с сервера нельзя — точка касания названа, класс открыт.

## 3. ПРЕДЛОЖЕНИЕ: третье состояние `(pass, notify)` — что потребует, где ломает

**Не применено. Ниже — цена, а не рецепт к немедленной правке.**

### 3.1 Форма

Вердикт становится ПАРОЙ вместо одного бита:

```
власть   ∈ {pass, block}
внимание ∈ {silent, journal, notify, ask}
```

Сегодня выразимы `(block, ask)`, `(block, silent)`, `(pass, silent)`. Добавляется ровно одна
клетка — `(pass, notify)`: «сделал, знай». `(block, notify)` не нужен: блок и так говорит.

**Хорошая новость:** на уровне ПРОТОКОЛА хука третье состояние выразимо уже сегодня — `_push(card)`
и `_defer()` независимы, ничто не мешает отправить карточку и выйти нулём. Ломается не протокол.

### 3.2 Где ломает (шесть мест, по убыванию цены)

1. **`_guard_monitor_loop` (демон, `:503-515`)** — маркер означает `terminate()`. Уведомление,
   написанное в тот же каталог, УБЬЁТ задачу. Нужен ВТОРОЙ канал-файл (напр. `/tmp/cc_guard_note/`),
   который монитор не читает вовсе, и `_guard_write_marker` с явным разделением назначения.
   Без этого пункта остальные бессмысленны.
2. **Замок происхождения (`_card_origin`, `_guard_what`, `process_approved`)** — штамп `🔒` даёт
   карточке право на исполнимый класс после «да». Заметка обязана быть третьим штампом (`🔔`) с
   fail-closed запретом: заметка НИКОГДА не открывает `EXECUTORS`, даже если владелец ответил «да».
   Иначе новый вид сообщения станет новым способом подделать разрешение.
3. **Приёмник ответов devbot (`_apply_verdict`, `_named_object_reply`, кнопки ✅/❌)** — сейчас
   любая карточка с номером ждёт решения. Заметка не должна иметь кнопок и должна получать
   конкретный отказ на «да N» («это заметка, решать нечего»), иначе класс 95/100 («✅ означало то
   одно, то другое») воспроизведётся с другой стороны.
4. **Напоминание «>3 ч без ответа»** — заметке не нужно; иначе тихий шум станет громким.
5. **Дедуп и объём.** 67 записей в мозг + 21 push + 12 рестартов за пять суток = ~100 сообщений,
   если слать по событию. Уведомление умрёт от шума ровно как рассылка. Нужен агрегатор **по
   задаче**: одна строка «что задача изменила в мире» в её же done-рапорте, а не событие на каждую
   команду.
6. **Доктрина в CLAUDE.md** («что именно владелец проверит своим „да“? нечего — ask не нужен»).
   У заметки ответ «ничего», и это законно. Не дописав доктрину, следующая ревизия снесёт заметки
   как «подтверждение, которое ничего не проверяет».
7. **Тест `test_no_push_leak`** («полный гейт → ноль исходящих пушей») — заметки обязаны быть под
   тем же мутом, иначе гейт начнёт писать владельцу.

### 3.3 Кого туда переселить (по замеру §2.2)

`(pass, notify)`: рестарт splinter и демона, `git push`/коммиты, правки дерева (`reset --hard`,
`checkout --`, вынос теста из гейта), удаления вне `/tmp` и удаление маркеров, записи в мозг —
агрегированно.
`(block, notify)` вместо нынешнего `(block, silent)`: 9 жёстких блоков и 5 `card_skipped` — сегодня
владелец не знает ни о блоке, ни о его причине.
**Не трогать:** `(block, ask)` для Лист1/CRM/денег/удаления событий и `deny` для секретов и боевых
процессов. Направление ошибки прежнее: заметка НЕ ДАЁТ НИКАКИХ ПРАВ.

### 3.4 Прецедент, который стоит расширить, а не изобретать

`(pass, notify)` в системе уже реализовано — ровно один раз и для одного случая:
`orchestrator_daemon.py:1209-1228`, `NA_PHRASE_NOTE` — «исход задачи остаётся честным, а сигнал
владельцу идёт заметкой». Слова о красной зоне в отчёте больше не рождают карточку и не подменяют
результат: задача завершается `done`/`failed`, а к рапорту клеится `⚠️`. Это и есть третья клетка.
Самый дешёвый первый шаг — не новый канал, а **сводка «что задача изменила в мире» в существующем
done-рапорте 328**: кнопок не требует, дедуп не ломает, монитор не задевает.
