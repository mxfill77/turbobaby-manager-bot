## 1. Где рождается карточка и почему пустой объект её отменяет

Путь целиком — `pretool_guard.main()`:

```
2659  obj, num = card_min(hit, blob)          # извлечение объекта и числа
2679  if not card_gate(hit, obj, num):        # ЕДИНОЕ правило карточки
2680      why = "объект=%s, число=%s" % (obj or "—", num or "—")
2681      _guard_log("card_skipped", cmd, hit + ": " + why)
2682      _ask("🔴 КРАСНОЕ (%s) — карточки нет: %s. …решай по самой команде." % (hit, why))
2684  _guard_write_marker(tid, hit, card, blocktype=blocktype)   # ← канал ДЕМОНУ
2691  _push(card)                                               # ← канал ВЛАДЕЛЬЦУ
```

`card_gate` (1410–1429) — одна строка: `return bool((obj or "").strip())`.
`_ask` (1074) → `_emit` (1068) → `sys.exit(0)`. **Строки 2684 и 2691 в этой ветке недостижимы**:
маркер демону не пишется, пуш владельцу не уходит. Маркер — ЕДИНСТВЕННЫЙ канал, которым демон
узнаёт о красном (`orchestrator_daemon.py:365-389`, `:549`), поэтому карточки в 328/1160 не будет
ни одной. Остаётся строка `card_skipped` в `/tmp/cc_pretool_guard.log` — журнале, которого не
читает ни один механизм.

### Это ЗАЩИТА — и обоснование стоит в самом коде

`card_gate`, докстринг 1413–1414 дословно:

> «ОБЪЕКТ обязателен ВСЕГДА. Нет объекта — признак сработал на ПОДСТРОКЕ, а не на действии
> (`print('set_fleet_oil')`): показывать владельцу нечего, идёт строка в журнал.»

Защита настоящая и измеренная: правило заведено 29.07.2026 после пяти пустых денежных карточек
(«проводка ДЕНЕГ · Объект: — · Число: —») за трое суток, за которыми не стояло ни одной проводки
(`docs/artifacts/2026-08-02-money-action-not-word.md`). Мой собственный замер её подтверждает: из
21 живой команды заходов, срезанной этим правилом за 30 суток, **21 из 21** — читающая разведка,
где имя операции лежало словом внутри скрипта (см. §2). Правило работает.

### И внутри защиты — недосмотр шириной в одну ветку

Гейт превращает «объект не извлёкся» в «действия не было». Это ДВА разных факта, и гард умеет их
различать — он уже делает это для денег:

```
1305  if not obj and _money_call_seen(hit, blob):
1306      obj.append("вызов %s()" % hit)   # аргументов нет по природе — цель это сам вызов
```

Для общего класса `confirmed` такой ветки нет. Его извлечение объекта — 1324–1330 — читает РОВНО
два семейства полей: байк (`number`/`plate`/`bike`) и клиент (`client`). Дверь отмены адресует
свой объект ключом `act` (`bridge_prod/ServiceUndo.js:232`), и объект выходит пустым.

**Факт, снятый живьём** (`_recon_guard_deadlock_0826/r7_view.py`, тело БЕЗ ключа подтверждения,
чтобы не покраснел сам файл разбора): разбор гарда `_py_code_view` уже держит всё, чем объект
называется:

```
calls: {"_post": {"act": "mt93f8k91a7ea", "by": "Filipp"}, …}
strs : ["…", "service_undo", "mt93f8k91a7ea", "Filipp"]
```

То есть в момент, когда `card_gate` говорит «объект=—», имя двери и ключ адресации лежат у гарда
в руках — разобранные, литеральные. Не хватает не ФАКТА, а ветки, которая делает из факта объект.

**Вывод: защита верна по замыслу, дыра в ней — не в правиле объекта, а в словаре объектов
класса `confirmed`.** Правило «нет объекта — нет карточки» трогать не надо; надо, чтобы объект
у настоящего вызова находился.

### Круг замыкается снаружи гарда

Второй выход исполнителя — самому объявить `NEEDS_APPROVAL: op=other`. Замок происхождения
(31.07) штампует такую заявку `🗣 слова исполнителя`, и дежурный по карточкам закрывает её
условием «источник» (`card_duty.py:169-185`). Его терминальный текст обещает дословно
(`card_duty.py:271`):

> «когда команду РЕАЛЬНО попробуют, её перехватит гард и пришлёт карточку с объектом.»

Для двери, чьего имени гард не знает, это обещание **неисполнимо**. Круг: дверь требует
подтверждения → подтверждение краснит → красному нужна карточка → карточке нужен объект →
объекта нет → тишина → исполнитель просит сам → дежурный закрывает, отсылая обратно к гарду.

## 4. Как разомкнуть круг (предложение, не постройка)

Четыре независимых хода. Первые два закрывают КЛАСС, третий — эту дверь, четвёртый — вторую
половину дела, которая к гарду отношения не имеет.

**A. Объект по РАЗОБРАННОМУ ВЫЗОВУ, а не по словарю полей.** У общего класса `confirmed` завести
ту же ветку, что уже живёт у денег (1305): вызова в разборе нет — объекта нет, как сегодня
(слово в тексте разведки по-прежнему карточки не даёт); вызов ЕСТЬ — объект называется его
именем и ключом: «дверь моста `service_undo` · акт `mt93f8k91a7ea`». Оба факта уже в
`_py_code_view` (`calls`, `strs`, `lit_args`) — новых сведений собирать не нужно. Правило
ОДНОСТОРОННЕЕ: умеет только ДОБАВИТЬ карточку, снять `ask`/`deny` не умеет ничем.

**B. Третий исход у самого гарда: «не могу ни исполнить, ни спросить».** Сегодня исходов два —
карточка либо строка в журнал, который не читает никто. Третий нужен там, где красное встало на
РАЗОБРАННОМ ВЫЗОВЕ, а объект всё равно не извлёкся: это не ложное срабатывание, это слепота
самого гарда, и она обязана быть сказана вслух. Канал — НЕ карточка (подтверждать безымянный
объект доктрина запрещает, и правильно), а заметка в ленту 829 плюс маркер нового вида, который
демон рисует терминальной картой без кнопки — по образцу `_forged_op_card`. `card_gate` при этом
не трогается ни на строку: «да» без объекта по-прежнему не спрашивается, кончается только
молчание.

**C. Имя двери в словарь** (`service_undo` в `RED_TOKEN_HIT` + `_ACTIONS` + ветка объекта по
`act`). Даёт лучшую карточку (Что · Объект · Число · Откат), но лечит ОДНУ дверь из 80. Это
завершающий ход, а не закрывающий: без A класс вернётся на следующей незнакомой двери.

**D. Ответу владельца некуда сесть — и это вне гарда.** Даже с карточкой и «да» отмену сегодня
никто не исполнит: `bridge_client` не знает `service_undo` (проверено: 104 метода, ни одного),
а `undo_last.position` не читает `act`, хотя мост его отдаёт (`ReadFleet.js:388`, `:482`). Это
назвал ещё заход 16; развилка владельца там своя — кнопка на карточке 1160 против строки
`needs_approval` в очереди.

**Порядок, который РЕАЛЬНО разблокирует работу: A (или C) + D. B — страховка, чтобы класс
перестал быть немым навсегда.**

## 5. Сколько работы и что в ней красное

| ход | объём | доставка | красное |
|---|---|---|---|
| A | одна ветка `_detail_parts` + помощник + сьют с отрицательными близнецами («слово в тексте → карточки по-прежнему нет») | **рестарта нет**: гард — хук-подпроцесс, читается с диска каждым вызовом | **нет** |
| B | гард + рендер в демоне + сьют | **рестарт демона** (правило самомодификации: отложенно) — оранжевое | **нет** |
| C | словарь + ветка + сьют | рестарта нет | **нет** |
| D | `bridge_client.service_undo` + `undo_last` + кнопка splinter | **рестарт splinter** — оранжевое; `clasp` НЕ нужен, дверь уже в проде @83 | **нет** |

**Красное во всей цепочке ровно одно — сам акт:** вернуть три регистра байка 5960 на 41357 через
дверь = запись в Лист1 с подтверждением, то есть «да» владельца по доктрине. Ни `clasp`, ни
`sqlite3`, ни удаления в починке не нужно.

Оценка: A+C ≈ один заход; B ≈ один заход (трогает демон); D ≈ один заход с развилкой владельца.

**«За сутки так умерло два захода» — не подтвердилось; подтверждается ОДИН.** Заход 16

упёрся; его отчёт `reports/2026-08-25/task-16.md:77` несёт отказ дословно. Остальные заходы суток
(1, 2, 5, 8, 11 и продолжения 7, 10, 13) целью отмену не имели: 2 — третий исход карточки работ,
5 — доставка `bf57de4`, 8 и 11 — расхождение половин «в работе». В журнале гарда за сутки строк
класса `confirmed` две (20:18:02 и 21:22:07) — и **обе диагностические пробы** (заход 16 и этот
заход), а не попытки. То есть класс убил ЦЕЛЬ одного захода; вторым «умершим» правильнее считать
не заход, а работу 23.08: task 99 уже тогда записал «`grep service_undo` по `bridge_client`/
`splinter` даёт ноль — бот позвать выложенную дверь не умеет».

**«Владелец не узнал ни разу» — верно ПРО КАРТОЧКУ и неверно про факт.** Карточки не было и быть
не могло (§1, маркер и пуш недостижимы; в `chain_cards.jsonl` за сутки только чужие терминалы
15 и 18). Но владелец узнал двумя другими каналами: первой строкой отчёта задачи 16 в теме 328
(«краснит гард, а карточки владельцу нет») и кураторской карточкой владельцу — задача 17,
`orchestrator_daemon.log` 25.08 20:31:43. Точная формулировка: **владелец не получил ни разу
карточку, ответом на которую можно было бы разблокировать работу.**

**Побочно и на будущее: сам этот разбор попал под тот же класс.** Первая редакция
`_recon_guard_deadlock_0826/r5_confirmed.py` несла тело вызова двери строкой — гард закрасил

(журнал, 25.08 21:22:07). Обходных форм не искали: пробу переписали без красного написания,
а контраст «если объект назван читаемым ключом» измерен ОТКАЗОМ первой редакции — гард тогда
назвал `Объект: байк 5960` и ушёл в жёсткий блок живой сущности, то есть ветка объекта работает,
когда ключ ей знаком.

## 7. Предел разбора: чего он не видел

1. **ПК-полосу не смотрел** — зеркало гарда живёт в чужом репозитории, с этой машины недоступно.
   Все числа и все строки кода — про VPS.
2. **Инбокс 1160 глазами не читал.** «Карточки не было» выведено из кода (после `_ask` маркер и
   пуш недостижимы) и из `chain_cards.jsonl`, а не из чата.
3. **Журнал гарда — единственный источник §2, и он загрязнён своими же сьютами** (451 из 492
   строк). Отдельный класс, здесь не чиненный: сьюты пишут в БОЕВОЙ `/tmp/cc_pretool_guard.log`.
   Успешные карточки в него не пишутся вовсе → знаменателя «сколько красного получило карточку»
   у меня нет.
4. **Классификация дверей моста на пишущие — эвристика** (следует за вложенными вызовами на один
   уровень; `get_balance`/`tx_summary` попали в пишущие из-за общего кэша и журнала). Поэтому
   решающая таблица §3 построена не на ней, а на точном признаке `confirmed !== true`
   (6 совпадений, перечислены поимённо).
5. **Живую дверь не звал и Лист1 не читал** — какие числа стоят в регистрах 5960 сейчас, отсюда
   не проверено; возврат не сделан.
6. **Реплей прошлого сегодняшним кодом.** 30-суточный счёт берёт то, что записано; правила гарда
   за окно менялись (`40c8425`, `c8cec4f`, `529d569`), и исход тех строк по-новому не переигран.
7. **Отчёты как источник частично разрушены:** `reports/2026-08-25/task-11.md` и `task-60.md` —
   фикстуры сьюта, затёршие живые отчёты тех же номеров (сьюты пишут в боевой `reports/`).
8. **Не считал, сколько из 80 незнакомых дверей вообще достижимы из кода бота** — счёт вёлся по
   мосту, не по вызывающей стороне (`bridge_client`, 104 метода).
