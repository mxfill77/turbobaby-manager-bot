**Живое доказательство из журнала — одна и та же тема 64, один и тот же читатель

| 2026-06-30 08:11:29 | `тема 64 (ADV 350 GREY 798)` |

## 3. ПУНКТ 2 — за семеро суток — **ОТСУТСТВУЕТ (проверить нечем)**

Это законная ветвь отказа, названная заданием, а не ноль.

**Записей обслуживания за 15.09–22.09: 12** (8 `service_upsert` регистра ТО + 4 строки
инфо-работ). По байкам: 7530, 5849, 5773, 4255, 8949, 798, 4255, 798 и четыре строки 798.

**Сколько из них ушло не тому байку — установить нечем, и причина устройственная:**

1. Значение, которое ложится в поле `bike`, **И ЕСТЬ** результат `bike_from_topic`, то есть кэш
   темы. Сравнивать его с «байком группы» тавтологично: они совпадают по построению всегда,
   включая случай, когда кэш протух.
2. Независимой истины — ЖИВОГО заголовка темы на момент записи — в данных нет нигде: ни в
   журнале, ни в листах. Строка журнала, где тема и байк стоят рядом
   (`🧩 Тема→байк (сервис-событие)`), встречается во всём журнале **2 раза**.
3. Строки «события» тему хранят (`splinter.py:2748`: `grp = group_name + f" / тема {topic_id}"`),
   а записи регистра ТО (`service_upsert`) **не хранят тему вовсе** — в журнале их строки
   темы не называют.

**Чего не хватает, чтобы ответить числом:** заголовка темы, снятого НЕЗАВИСИМО от кэша в момент
записи, и сохранённого рядом со строкой. Сегодня записывается только то, что система сама же и
вывела, поэтому расхождение принципиально невидимо для неё.

Единственное расхождение, которое сегодня было бы видно, — когда байк назван ТЕКСТОМ и не
совпал с темой (`parsed.get("bike")` победил). Но журнал не печатает оба значения рядом, и за
7 суток таких пар в нём нет.

## 5. ПУНКТ 4 — какой источник пробега победил — **НАЙДЕНО**

**Победило число от человека — 27537.**

Единая точка решения, `splinter.py:3181-3188`:

```python
def _km_for_record(parsed, vis):
    return str((parsed or {}).get("mileage") or "")
```

В запись идёт ТОЛЬКО `parsed.mileage` — число из текста. Сырой разбор фотографии (`vis.mileage`)
не пишется ни по одному пути; `vis` принят аргументом намеренно, чтобы место решения было видно
и ветку нельзя было «дочинить» мимо него. Журнал это подтверждает: обе величины эпизода помечены
`(подтверждено человеком)`.

**Может ли разбор картинки поднять пробег БЕЗ подтверждения человеком: НЕТ** — по пути записи.
Подтверждённое фото-число входит только через `_ask_mileage_confirm → handle_mileage_confirm`
либо кнопку → `_odo_confirmed`.

**Негодный признак назван.** Запрета на ПОКАЗ у OCR-числа нет: в 12:45 ответ назвал человеку
пробег 27464, взятый с фотографии, вместе с именем байка — и ничем не пометил, что это ещё не
подтверждённое число, а догадка по снимку. Показ не есть запись, но человек читает показанное
как записанное; признак «это OCR, он ждёт твоего „да“» в тексте ответа отсутствует.

## 6. ПУНКТ 5 — тайский и русский перечни — **НАЙДЕНО. Один список, ДВА рендера**

Список работ один — `works`. Оба перечня строит `splinter.msg_works_logged`

**Место 1 — русский**, `splinter.py:1957`:


дедуп по РУССКОЙ строке.

**Место 2 — тайский**, `splinter.py:1958` → `_works_th_str` (`splinter.py:2047-2052`):

```python
return ", ".join(dict.fromkeys(_work_th(w) for w in (works or []) if str(w).strip()))
```

дедуп по ПЕРЕВОДУ. Расхождение заложено и названо в его же докстринге дословно: «Разные работы
с одним переводом (два синонима масла) → один лейбл».

**На этом случае оно и сработало, и причина — в правиле отбора стема**, `splinter.py:2019`:

```python

    if k in s:
        return _WORK_TH[k]
```

Стем выбирается САМЫЙ ДЛИННЫЙ из подошедших, а не первый по словарю. В строке «набивка смазки
вариатора» подходят два: `"вариатор"` (8 знаков) и `"смазк"` (5) — побеждает `"вариатор"`.
«Чистка вариатора» даёт его же. Обе работы получают один лейбл `ชุดสายพาน` и схлопываются.

Полный перечень случая: замена шины → `"шин"` → `ยาง`; замена комплекта подшипников →
`"подшип"` → `ลูกปืน`; чистка вариатора и набивка смазки вариатора → оба `ชุดสายพาน`.
**Русских пунктов 4, тайских 3.**

**Третье обстоятельство той же пары:** неизвестные работы переводит языковая модель —
`_learn_works_th` (`splinter.py:2026-2044`), один вызов на запись, результат живёт в
