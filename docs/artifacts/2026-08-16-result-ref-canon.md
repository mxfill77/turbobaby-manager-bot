# ФОРМА АДРЕСА РЕЗУЛЬТАТА СВЕДЕНА К КАНОНУ (16.08.2026)

Одна цель: **синтаксис маркера, имена видов и их разбор**. Вердикт шага не тронут, третьего
исхода нет, правило «нет адреса — нет зелёного» не включено, ни одно место, судящее по отчёту,
не правлено. Пункты 2–5 контракта третьего исхода — следующие заходы.

## 1. Повод — живой факт: одно поле, две формы

Пункт 1 контракта сделан на ОБЕИХ полосах, и формы разошлись:

| полоса | коммит | маркер | пятый вид |
|---|---|---|---|
| VPS (эта) | `7f147a0` | `[адрес результата: <вид> <указатель>]` | `service_start` |
| ПК (отсюда не проверяется) | `6cb2a70` | `<вид>:<указатель>` | `service` |

Пункт 3 контракта требует, чтобы обе полосы читали ОДНО И ТО ЖЕ. Две формы этого требования не
выполняют: строку соседней полосы каждая сторона прочла бы как «адреса нет».

**ЗАЩИТА ОТ ПОВТОРА (первое действие захода).** Маркер имел вид `[адрес результата: …]` —
не канон; пятый вид уже звался `service_start`. Условие остановки требует ОБОИХ признаков,
поэтому заход продолжен.

## 2. Канон, назначенный Штабом (обязателен дословно)

```
[result_ref: <вид> <указатель>]
```

* ключ `result_ref` — латиницей;
* после вида разделитель — **ПРОБЕЛ**;
* виды: `commit` · `file` · `row` · `brain` · `service_start`.

**ПОЧЕМУ ПРОБЕЛ, А НЕ ДВОЕТОЧИЕ.** Указатель вправе нести двоеточие ВНУТРИ себя: на соседней
полосе это виндовый путь (`C:\Users\…\pc_orchestrator.py`), здесь — ключ строки
(`очередь[10]: колонка result`) и раздел узла мозга. Деление по двоеточию порвало бы такой
указатель пополам и вернуло не то, что клали, — то есть завело бы класс «читатель тихо портит
факт». Пробел таких указателей не встречает: вид отделяет ПЕРВЫЙ пробел, дальше указатель идёт
целиком, до последней «]» строки.

## 3. Замер ДО правки: нужна ли совместимость со старой формой

Читающий снимок ЖИВОЙ очереди (16.08.2026, `get_pending` по каждому из семи статусов,
`lane=all`; ни одной записи, ни одного удаления):

| что считали | число |
|---|---|
| вызовов, ПИШУЩИХ адрес | **0** (дверь записи одна — `bridge_client.enqueue_task(..., result_ref=…)`; ни один вызов репозитория её не называет; проверено grep + ast-стражем сьюта) |
| строк очереди, НЕСУЩИХ адрес старой формы VPS | **0** |
| строк очереди, НЕСУЩИХ адрес формы ПК | **0** |
| строк очереди, НЕСУЩИХ канон | **0** |
| **знаменатель: строк очереди прочитано ВСЕГО** | **6** (id 1…6 подряд, все семь статусов ответили `ok`, ни один не промолчал) |

Знаменатель назван намеренно: ноль без него ничего не стоит. Первый прогон дал 6 строк против
сотен в прошлых снимках — это проверено вторым, разбивочным прогоном: очередь ПЕРЕСОЗДАНА, в
ней сегодня шесть строк 16.08 (четыре `done`, две `in_progress` — задачи этого контракта на
обеих полосах), усечения ответа нет.

**ВЫВОД, СКАЗАННЫЙ ПРЯМО: совместимость со старой формой НЕ НУЖНА и НЕ ЗАВЕДЕНА.** Понимать
по-старому нечего — ни одной живой строки. Две формы означали бы два способа сказать одно ровно
там, где контракт требует одного. Появись хоть одна живая строка — в модуле стояла бы ветка
чтения старой формы с названным числом таких строк; её нет именно потому, что число ноль.

Обе прежние формы теперь адресом НЕ считаются, и это ВИДНО, а не молчит: `parse` отдаёт `None`
(«адрес не назван») — законное сегодняшнее состояние каждого шага.

## 7. Остатки

* **Полосу ПК к канону приводит ЕЁ заход** — эта машина её кода не видит вовсе. Точки касания
  там: модуль формы, дверь записи в клиенте моста, имя пятого вида (`service` → `service_start`),
  разделитель (двоеточие → пробел). Пока он не сделан, адреса соседней полосы здесь не читаются,
  и это ВИДНО (`None`), а не искажается молча.
* Адрес по-прежнему не заполняет ни одно место — это пункты 2–5 контракта.
* Класс «фикс в git ≠ фикс в проде» ДЕЙСТВУЕТ на дверь записи (`bridge_client` живёт в памяти
  `splinter` и демона); доставка — отдельной карточкой. На поведение это не влияет, пока адрес
  не пишет ни один вызов.
* Замер «0 строк из 6» снят с очереди, ПЕРЕСОЗДАННОЙ 16.08: он говорит о сегодняшней очереди, а
  не о всей истории — но именно сегодняшнюю и придётся читать.
