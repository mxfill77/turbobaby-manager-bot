### Какой именно код он прочитал при старте

```
$ git hash-object orchestrator_daemon.py     → 993721bdaf82109d5070ba4a80424cc33e49ab49
$ stat -c %y orchestrator_daemon.py          → 2026-09-19 17:41:21 +0000

```

Три факта вместе закрывают вопрос:

1. **mtime файла СТАРШЕ старта на 20 ч 31 мин 55 с.** Python читает `.py` один раз, при старте;
   значит байты, лежащие на диске сейчас, и есть те, что процесс прочитал тогда.
2. **После старта ни один модуль корня не менялся** (`find -newermt` пуст) — дерево за спиной
   процесса не убежало, и «диск сейчас» законно говорит о «диске тогда».
3. **Файлы демона побайтно равны `origin/main`** — `git diff --stat origin/main -- '*.py'` их не
   называет вовсе.

Честная оговорка о расхождении диска: четыре файла от `origin/main` всё же отличаются —
`park_read.py`, `park_verdict.py`, `splinter.py`, `tests/test_park_read.py` (незакоммиченная
работа читателя парка). **К вердикту они не относятся: демон не импортирует ни один из них**
(проверено `grep` по его исходнику — ни `park_read`, ни `park_verdict`, ни `import splinter`).

### Что было проверено и оказалось НЕ различителем

Коммит `5e78c36` добавил дочернему `claude -p` аргумент `stdin=subprocess.DEVNULL`, и соблазн был
прочитать свой собственный `stdin` как отпечаток версии. Проверено:

```
$ readlink /proc/self/fd/0      → /dev/null      (я, дитя демона)
$ readlink /proc/2214559/fd/0   → /dev/null      (сам демон)
```

**Свидетель негоден:** у демона `stdin` тоже `/dev/null` (умолчание systemd — `StandardInput` в
юните не задан), поэтому простое наследование дало бы ту же цель, и старый код неотличим от
нового. Различить их можно было бы флагами открытия (`O_RDWR` у `subprocess.DEVNULL` против
`O_RDONLY` у systemd), но `/proc/*/fdinfo` закрыт песочницей рабочих каталогов, а пробных
скриптов заход запускать не вправе. Записано как проверенный и отвергнутый ход, а не как довод.

## 3. ПРИЗНАК В ДЕЛЕ — какой из двух способов стоит в исполняемом коде

**В исполняемом коде стоит НОВЫЙ способ — поля конверта.** Прочитано в тех самых байтах, что
держит процесс:

```
orchestrator_daemon.py:57    import limit_slot
orchestrator_daemon.py:1733  _lim = limit_slot.plan(_parsed, child_env, retried=bool(_slot))
limit_slot.py:105            if "is_error" not in parsed:
limit_slot.py:108            if parsed.get("is_error") is not True:
limit_slot.py:111            status = _int_or_none(parsed.get("api_error_status"))
limit_slot.py:62             LIMIT_STATUSES = frozenset((429,))
```

**Старый способ не удалён, но роль у него другая — и это важно не спутать.** Английский текст
жив на прежнем месте:

```
status_truth.py:95   if any(n in blob for n in _MODEL_NEEDLES): return "model_refusal"
```

и демон по-прежнему его зовёт — строкой **1742**, на девять строк НИЖЕ нового признака:

```
orchestrator_daemon.py:1742  _set_fail_code(_mctx, status_truth.classify_exec(out, err, proc.returncode))
```

Порядок в живом коде такой: сперва **машинное поле решает про лимит и повтор** (1733), потом
**английский текст ставит код причины** (1742). То есть коммит не заменил один способ другим, а
**отнял у текста решение о лимите**, оставив ему прежнюю работу — называть код причины. Ровно
это коммит и обещал в своём сообщении.

`tokens_in=0 tokens_out=0` при `dur_s=19.80` — тот самый отпечаток, который новый признак и
заведён ловить машинным полем.
