### Счётчик смертей — есть, но СВОЕЙ формы не имеет

`смерть 1/3` · `смерть 2/3` · `умер 3 раза подряд` — это **поле внутри** форм A и B. Отдельной
записи «у ребёнка N смертей» в журнале нет: счётчик виден только тогда, когда что-то уже
случилось. Его обнуление (`deaths=0 halted=false`) встречается лишь в **прозе** отчётов
(`RC 2026-08-05 00:56`), то есть машинно-разбираемой формой не является.

## 2. Периодический признак живости: ЕСТЬ — но о ДЕМОНЕ, а не о детях

Журнал **не только событийный**, и это надо сказать точно, иначе ответ будет неверен в другую
сторону. Периодическая форма существует — 22 записи:

```
NOTE 2026-08-16 07:24 UTC: ПУЛЬС · ПК · контур жив: оборот poll_once 0 мин назад · следа работы в журнале нет 12 ч 9 мин (порог пульса 360 мин) · это след ЖИЗНИ, а не отчёт о работе: пишется только при ДОКАЗАННОМ обороте, поэтому его молчание значит «ПК не даёт оборота», а не «задач не было»
```

Свойства пульса, снятые с корпуса:

* **предмет — `poll_once`, оборот демона `pc_orchestrator`.** О `userbot_listen` и
  `moderation_bot` в нём НЕТ НИ СЛОВА. «Контур жив» здесь означает «демон даёт оборот»;
* **шаг 30 мин**, окно 14.08 23:24 → 16.08 07:24, все 21 паузы = 0.50 ч;
* **пульс УСЛОВЕН:** пишется только когда следа работы нет дольше 360 мин. В рабочее время его нет
  вовсе — с 16.08 07:24 до конца окна (2.17 суток) ни одного пульса, потому что полоса работала.

**Вывод по пункту 2, прямо:** о клиентских детях журнал говорит **ТОЛЬКО СОБЫТИЯМИ** — подъём,
стоп, плановый рестарт. Периодического признака их живости нет ни одного.

**Поэтому судить живость детей по отсутствию записей о смерти НЕЛЬЗЯ**, и вот два измеренных
довода, а не рассуждение:

1. **Вердиктов о живости ребёнка в заявляющей позиции — 0 за 20.8 суток.** Ребёнка называют 46
   строк из 664, и все 46 — это A/B/D/E либо проза отчёта задачи. Ни одной формы «ребёнок жив» /
   «ребёнок не даёт тика».
2. **ПАРАДОКС О4, проверенный живым кодом:** `cowork_facts` берёт МАКСИМУМ времени по всем строкам,
   то есть любая строка есть «след жизни ПК». Прогон по одной лишь записи о смерти:

```
если бы в журнале была ТОЛЬКО запись «вотчдог поднял moderation_bot»:
   cowork_facts.last = 2026-08-18 07:39 UTC  → для О4 это СВЕЖИЙ СЛЕД, то есть ПК ЖИВ
```

   Запись о **смерти** ребёнка обновляет признак жизни полосы и **снимает** подозрение О4.

## 3. Собрать ожидание по контракту — НЕЛЬЗЯ. Недостающий признак назван

Контракт требует четырёх вещей. Три из них не выполняются:

* **ожидаемый результат** — должен быть НАБЛЮДАЕМЫМ, пока нарушение идёт. Здесь длительность
  (`лежал 12 ч 10 м`) публикуется **ТОЛЬКО в момент подъёма**, ретроспективно. Пока ребёнок
  лежит, журнал о нём молчит;
* **источник** — молчит именно о том, о чём надо судить, и молчание это НОРМА: о детях говорится
  9 раз за 20.8 суток, то есть раз в ~2.3 суток;
* **отрицательный тест** — провалится по построению: «журнал молчит о детях N часов → тревоги
  нет» верно для подавляющего большинства времени.

**Живой контрпример, снятый по окну инцидента.** Ребёнок умер ≈17.08 19:29 UTC (07:39 минус
12 ч 10 м). Полоса в это время была **ЖИВА и писала**:

```
08-17 19:37 | задача #40 → done
08-17 20:06 | взял задачу #41 (in_progress)
08-17 20:27 | задача #41 → done
08-17 20:56 | взял задачу #43 (in_progress)
   ← далее 10 ч 17 м НИ ОДНОЙ строки: демона убила двойная перезагрузка Windows
08-18 07:13 | watchdog: поднял демон через schtasks (лежал 10 ч 19 м, …)
08-18 07:39 | вотчдог поднял moderation_bot (смерть 1/3, лежал 12 ч 10 м, …)
```

Четыре записи за 1 ч 27 м при живом канале и живой полосе — и **ни одна не о мёртвом ребёнке**.
Ребёнок умер РАНЬШЕ демона примерно на 1.5 часа.

**Что построить МОЖНО, и это надо назвать честно:** ретроспективный вердикт «подъём назвал
длительность больше N» — он даёт владельцу узнать о 12-часовом простое (сегодня не узнаёт вовсе),
но на 18.08 он заговорил бы в **07:39**, то есть ровно тогда, когда всё уже кончилось. Это
громкость постфактум, **не ожидание живости**.

### Недостающий ОДИН признак (только называю, не строю)

**Полоса ПК должна публиковать в общий журнал периодический ПУЛЬС О ДЕТЯХ — той же формы, что уже
публикует о демоне,** с ПРОДУКТОМ ЖИЗНИ каждого ребёнка. Например одной строкой рядом с
существующей: `ПУЛЬС · ПК · дети: moderation_bot тик N мин назад · userbot_listen тик M мин назад`.

Признак назван так, а не «процесс есть в списке», не по вкусу — этот выбор на ПК уже сделан и
записан в журнал:

```
NOTE 2026-08-11 09:19 UTC: Orchestrator: задача #491 → done · О3 поднят: судит ПРОДУКТ пятисекундного тика модербота (запись в `moderation_ipc`), а не живой PID. Порог 15 мин снят собственным замером бота, три исхода покрыты тестом в обе стороны, наблюдатель — уже стоящая задача SYSTEM вне модербота. Коммит `2239c65` запушен…
DONE 2026-08-11 09:18 UTC: Dispatch 16:30: О3 — ожидание на модербота поднято, коммит 2239c65 (запушен). Предмет — ПРОДУКТ пятисекундного тика (запись в moderation_ipc, читаем os.stat, базу не открываем), а не живой PID: залипший event-loop остаётся в списке процессов, и контур-вотчдог демона такой считает здоровым. Порог 15 мин снят СВОИМ замером (849 пауз лога модербота: max законной 5.022с; 26 промахов планировщика за 39 суток: худший 4.97с …
```

**То есть прибор на ПК УЖЕ ПОСТРОЕН — 11.08, коммит `2239c65`, порог 15 мин.** Не хватает не
измерения, а **публикации его вердикта наружу**: за 20.8 суток в журнале **ноль** его вердиктов.
Работа для соседней полосы — одна строка периодического следа, а не новый прибор.

## 5. Не дублирует ли будущее ожидание уже поднятые — проверено по коду, а не со слов

Действующих ожиданий девять (`expectations.KINDS`), плюс соседний детектор `prod_drift`:

| Ожидание | Предмет | Накрывает случай? |
|---|---|---|
| `o1_new_vps` | строка `new` полосы **VPS** не взята | нет — другая полоса |
| `o2_daemon` | оборот `cycle()` демона **VPS** | нет |
| `o2_splinter` | тик `devbot_report` **splinter** | нет |
| `o3_undelivered` / `o3_unknown` | коммит не доехал до прода **VPS** | нет |
| `o4_pc_silent` | ПК не оставил **ни одного следа** 16 ч | **нет, и хуже — см. ниже** |
| `o5_bridge_down` / `o5_bridge_slow` | мост | нет |
| `o6_pc_task` | **взятая задача** без записи об исходе | **нет** |
| `prod_drift` | живой процесс VPS отстал от git | нет |

**О6 — проверено кодом, а не поверено на слово.** `pc_lane_facts` возвращает ключи
`['answers', 'closed', 'lost', 'open', 'takes']` — **поля о детях в разборе полосы нет вовсе**, а
`pc_task_state` при отсутствии взятой задачи отдаёт `PCT_MOVING` с причиной «ни одной взятой
задачи — полосе не давали работы» (`expectations.py:1438`). Мёртвый ребёнок при пустой очереди для
О6 — «движется».

На живом случае О6 **сработал** — но по задаче #43 (10 ч 17 м при пороге 210 мин), а не по
ребёнку; и ребёнок умер в 19:29, тогда как задача взята в 20:56, то есть **1 ч 27 м он лежал
раньше, чем у О6 вообще появился предмет**.

**О4 не просто не накрывает — он работает ПРОТИВ.** Порог 16 ч больше живых 12 ч 10 м, но дело не
в пороге: предмет О4 — любая строка полосы, а запись о смерти ребёнка сама и есть строка полосы.
Проверено прогоном (пункт 2): она обновляет `cowork_facts.last` и **снимает** подозрение О4.

**Вывод: дублирования не будет ни с одним из девяти.**

## 6. Предсмертный взгляд одной строкой

Ожидание построят на записях **вотчдога** — и оно ослепнет ровно там, где простой самый длинный:
вотчдог либо заглох после трёх смертей («СТОП, нужен разбор» — 2 раза за окно, и оба эпизода
остались без длительности вовсе), либо умер вместе с машиной (18.08 — 10 ч 17 м без единой
строки), — то есть прибор промолчит именно тогда, когда ребёнок лежит дольше всего, и это
молчание прочитают как «всё хорошо».
