## 3. Ход A — как именно называется объект

Красное класса `confirmed` рождает ДЕЙСТВИЕ — вызов двери, требующей подтверждения. Разбор тела
(`_py_code_view`) уже держал всё, чем объект называется, но НЕСВЯЗАННО: `calls` — аргументы без
селектора, `lit_args` — литералы без привязки к вызову. Здесь три факта связываются с конкретным
вызовом (`_conf_call` → паспорт `{name, sel, args}`), а `_door_bits` делает из паспорта объект:

* **имя двери** — сам вызов (`bridge.set_caps(…)`) либо литерал-селектор доставщика
  (`_post("service_undo", …)`, `post(url, {"action": "service_undo", …})`). Различитель «селектор
  действия» не новый: им с 04.08.2026 живёт `_name_is_action`;
* **адрес операции** — первый НЕслужебный литеральный аргумент (`ключ act=…`, `ключ ref=…`).
  Служебные ключи протокола (`action`, `token`, `origin`, `ticket`, `by`, `key`, …) в объект не
  идут никогда — вместе с ними отсекаются носители секретов, и это проверено приманкой: значение
  `token='СЕКРЕТ-XYZ'` в объект не уезжает.

**Ветка ОДНОСТОРОННЯЯ и по устройству, а не по обещанию:** зовётся только при ПУСТОМ объекте
(подменить прежний нечем), умеет добавить карточку и не умеет снять `ask`/`deny`.

**Защита не ослаблена.** Требуется РАЗОБРАННЫЙ вызов с подтверждением в исполняющей позиции.
Разбора нет (heredoc/stdin/нечитаемый `.py`) · вызова нет (написание лежит ДАННЫМИ) ·
подтверждение вычисляется, а не литерал → объекта нет, как не было: строка в журнал, решение `ask`
остаётся. Из 21 живой команды, срезанной правилом объекта за 30 суток, 21 была читающей
разведкой — ни одна вызова подтверждения не несёт.

**Главная ловушка (та же, что у хода C) обойдена тем же способом:** `_entity_blocktype` судит ТЕМ
ЖЕ извлечением, но там «объект есть» = **deny без кнопки**. Ветка живёт под флагом `doors`, а
забор зовёт `_detail_parts(hit, blob, doors=False)` — для всех трёх новых форм забор по-прежнему
не видит объекта и `hard` не выносит (проверено попарно), а живая сущность парка жёсткий блок
получает, как получала.

## 4. Ход D — ответу владельца есть куда сесть

Сквозной путь, и каждое звено настоящее:

```
расписка записи регистра (act/act_logged, ReadFleet.js:388 и :482)
  → undo_last.position   — помнит ключ акта (раньше выбрасывала)
  → undo_last.act        — журнал акта темы
  → undo_last.request    — ответ владельца → тела вызовов + НАЗВАННЫЕ отказы
  → bridge_client.service_undo — POST {action: service_undo, act, by, confirmed}
  → serviceUndo_ (ЖИВОЙ код моста, bridge_prod/@83) — вернула кол.J 41667 → 41357
```

`request` ничего не подразумевает: подтверждение приходит РОВНО из ответа владельца, без него тело
строится с `confirmed=False` и рядом стоит причина («дверь ответит `not_confirmed` и НЕ пишет»).
Ключа акта нет (мост не записал память — `act: null`) → вызова нет и **это сказано**, а не
пропущено молча. Замки «последняя · своя · окно 3 ч · отмена отмены» живут в `verdict` и здесь НЕ
дублируются — второй их список разошёлся бы с первым.

Числа снаружи дверь не принимает вовсе — проверено составом тела: `token, action, act, by,
confirmed, origin`, ни `km`, ни `oil_km`.

## 6. Остатки — что этот заход НЕ закрыл

1. **Кнопки исполнения в `splinter` нет.** `_svc_undo_ask` по-прежнему только СТРОИТ карточку
   владельцу и не делает ни одного вызова записи (ast-страж в `tests/test_undo_last.py` цел).
   Заход дал ответу владельца АДРЕС (`request` → `service_undo`), а не нажатие. Точки касания:
   `splinter.handle_service_button` (ветка «да» на карточке отмены) и `_svc_undo_ask`.
2. **Живым случаем ветка A не проверена ни разу** — все числа сняты прогонами и харнессом; за 30
   суток класс населён семью командами. Первая настоящая карточка по незнакомой двери ещё впереди.
3. **Замер на живом корпусе (`guard_replay`, 16 433 команды) здесь НЕ повторялся** — заход
   уложился в бюджет за счёт того, что мерил прогонами «до/после» на дословных формах. Ход C свой
   замер прошёл (`2fe3513`), и ветка A уже его населения не касается: на всех командах, где объект
   называют поля, она молчит по устройству.
4. **Третьего исхода у гарда по-прежнему нет** (ход B разбора): красное на разобранном вызове, у
   которого объект всё равно не извлёкся (например, все аргументы вычисляются, а дверь названа
   переменной), остаётся строкой в журнал, которого не читает ни один механизм.
5. **Зеркала ПК-полосы нет.** Точки касания там: `_conf_call`/`conf_calls` в разборе тела,
   `_door_bits` и место её зова в `_detail_parts`, флаг `doors`.
6. **Разведка захода лежит в `_recon_guard_unlock_0826/` в корне репозитория, а не в
   `/tmp/tb_scratch`** (правило R17): песочница движка запрещает запись вне рабочих каталогов,
   `mkdir /tmp/tb_scratch` отклонён живьём. Каталог не удалялся (удаление вне временных каталогов —
   красная зона владельца); в нём же остался `git worktree` дерева `2fe3513` (`head_tree/`) для
   воспроизведения прогона «до».
7. **Сьют «до» тем же файлом не гоняется по устройству, и это названо прямо:** запуск
   `tests/test_guard_unlock.py` ИЗ каталога worktree получает от гарда жёсткий блок живой сущности
   (в файле есть фикстура записи по номеру парка, а ранний defer положен только целям под
   `PROJECT/tests/`), плюс у того дерева нет ни харнесса, ни помощника. Поэтому «до» измерено
   отдельной пробой на тех же дословных формах.
