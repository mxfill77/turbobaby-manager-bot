# Состояние серии — в файле демона, вне очереди; и сверка, которая умеет краснеть

**Дата:** 10.08.2026. **Повод:** рамка §8г («исход известен демону в момент терминала — там и
писать»); задача 451 умерла по таймауту, неся пять целей разом, и её работа закреплена коммитом
`5629a6c` как есть. Здесь ОДНА цель — состояние серии в файле демона. Сортировка вмешательств и
порог веса не тронуты намеренно: отдельные заходы.

## 1. Что уже стояло и чего не хватало

Коммит `5629a6c` принёс руки счёта в демон (`_series_note_card` / `_series_note_terminal` /
`_series_cards_tick` / `_series_derive`), файл `chain_series.json` рядом с демоном и пересчёт
снимком (`chain_series_report.py`). То есть пункты 1 и 2 задания в основном стояли. **Не стояло
пункта 3 — сверки.** Прежняя `--verify` печатала две пары чисел и **возвращала 0 всегда**:

```
СВЕРКА с файлом демона: живой current=1 best=1 chains=1 | пересчёт current=1 best=1 chains=285
```

Расхождение здесь не отличалось от совпадения ни кодом, ни словом — то есть сверки не было,
была строка о сверке.

## 2. Живой факт, найденный по дороге: боевой файл держал след ПРОБЫ

Боевой `chain_series.json` на начало захода (сохранён дословно в
`_scratch_series_file_0810/chain_series.json.before-install`):

```json
{"chains": {"101": {"root": 101, "lane": "vps", "created": "", "closed_at": "2026-08-10T18:25:00",
 "statuses": {"101": "done"}, ...}},
 "windows": [{"root": 101, "lo": "2026-08-10T17:48:57", "hi": "2026-08-10T17:48:57"}, ...],
 "started_counting": "2026-08-10T17:52:10Z"}
```

Признаки подделки видны прямо в теле: `created` пуст, все пять окон исполнения нулевой длины.
**Демон этого написать не мог:** боевой процесс поднят `2026-08-10 08:08:56 UTC`, кода счёта в
памяти не имел вовсе (в `orchestrator_daemon.log` — ни одной строки «СЕРИЯ»), а файл записан в
18:25, через минуту после коммита `5629a6c`. Значит боевое состояние метрики целиком было следом
харнесса, запущенного руками.

Ни один из четырёх признаков изоляции проб такой запуск не несёт (`venv/bin/python3 своя_проба.py`
не ставит ни `ORCH_TEST_MODE`, ни `PYTEST_CURRENT_TEST`), поэтому лечится это не окружением, а
**личностью пишущего**: `_IS_DAEMON` ставится в `main()` демона, и боевой путь отдаётся только
ему; всякий импорт со стороны пишет во временный файл. Направление ошибки названо: промах этого
рубежа стоит СЧЁТА (демон писал бы во временный файл), а не подлога в боевом, и виден он первой же
сверкой.

## 3. Сверка: три исхода, и ни один из них не правит файл

`chain_series_report.py --verify [--state PATH]` возвращает **0 сходится · 1 РАСХОЖДЕНИЕ ·
2 НЕ СВЕРЕНО**. Третий исход — тот же замок против ложного зелёного, что у О3/О4/О5: пустое
пересечение, непрочитанный журнал юнитов, непрочитанные окна исполнения и пустой файл дают
«не сверено», а не «сходится».

**Файл не правится ни при каком исходе** — это устройство, а не обещание: ast-страж секции (1)
`tests/test_chain_series_verify.py` доказывает, что во всём модуле сверки нет ни одного пишущего
вызова (`open` на запись, `json.dump`, `os.replace/remove/rename`, `shutil.*`), а секция (6)
сверяет sha256 файла состояния до и после КРАСНОГО прогона.

Что судится и чем:

| Слой | Что сравнивается | Красное когда |
|---|---|---|
| файл сам себе | `derived` против пересчёта из его же цепочек (`chain_verdict`+`series`) | числа не выводятся из фактов файла — правка руками |
| форма записи | у цепочки файла есть дата рождения | `created` пуст — писал не демон |
| цепочка к цепочке | обрыв и его причина на общей почве | обе стороны разобрали ОДНУ запись и судили её по-разному |
| числа | `series()` по одному набору корней с обеих сторон | разошлись при нулевой слепоте и нулевой приписке |

**Асимметрия слепоты названа прямо и считается числом.** Реплей структурно слеп там, где очередь
затёрла тело карточки её же вердиктом (замер 10.08: тело восстановимо у 46 вмешательств из 106) —
ровно поэтому файл и заведён. Поэтому «файл видит обрыв, реплей молчит» расхождением **не**
является, если реплей той записи не разобрал вовсе или разобрал как «неизвестно». Обратное —
«реплей доказал обрыв, файл его не знает» — **красное всегда**: это направление, в котором счёт
надувает серию, и слепотой оно не оправдывается ничем.

**Приписка ремонта руками по цепочке не сверяется** — сверяется её число. Перезапуск юнита своего
номера в очереди не имеет, и хозяина ему обе стороны назначают условно (демон — последней своей
цепочке, реплей — живой в ту минуту), о чём обе говорят прямо в коде. Сверять условное с условным
значило бы печатать красное на ровном месте.

## 4. Числа задания (пункт 4)

**Файл сразу после установки** (`_scratch_series_file_0810/install_state.py`, 19:30:55 UTC):

```json
{"started_counting": "2026-08-10T19:30:55Z", "chains": {}, "windows": [],
 "derived": {"chains": 0, "current": 0, "best": 0, "best_ever": 0, "last_break": null,
  "line": "серия цепочек: идёт 0 (вес 0 из 0 наблюдаемых), лучшая 0, всего цепочек 0, обрывов 0
           [шум 0 · ремонт 0 · отказ 0], вес по наблюдаемым 0.0%"}}
```

**Сходится ли с реплеем — НЕ СВЕРЕНО, код 2** (снимок очереди 285 цепочек, 451 запись):

```
СВЕРКА: НЕ СВЕРЕНО — в файле ноль цепочек: счёт установлен, но ещё не считал.
Сходимостью пустое пересечение не объявляем
КОД ВОЗВРАТА СВЕРКИ: 2
```

Это честный ответ, а не зелёное: сверять пока нечего. **Что сверка умеет — доказано на том же
корпусе живьём**, на прежнем содержимом того же файла (воспроизводится командой с `--state`):

```
СВЕРКА: цепочек в файле 1 · в снимке 285 · общая почва 1 (вне окна файла 284 · не сравнимы 0 ·
слепота реплея 0 · приписка ремонта 0)
  на общей почве: файл current=1 best=1 обрывов=0 | реплей current=1 best=1 обрывов=0
  РАСХОЖДЕНИЕ: цепочка 101 в файле БЕЗ ДАТЫ РОЖДЕНИЯ — живой счёт так не пишет:
               состояние правлено не демоном
ИТОГ СВЕРКИ: РАСХОЖДЕНИЕ (1) — красное. Файл НЕ правим
КОД ВОЗВРАТА СВЕРКИ: 1
```

**Отдельно стоит запомнить, ПОЧЕМУ понадобилась проверка формы:** по ИСХОДУ подделка сошлась.
Синтетическая цепочка 101 («done, обрывов нет») совпала с настоящей цепочкой 101 из очереди, и
первая редакция сверки вернула на ней **зелёное**. Сверка по исходу ловит спор о мире, но не
ловит подлог, случайно совпавший с миром; ловит его форма записи — дата рождения, которую даёт
запись очереди.

## 5. Что ещё изменилось в файле (пункт 1 задания дословно)

* `series()` отдаёт **`last_break`** — дату последнего обрыва и его сорт отдельным полем, а не
  хвостом списка;
* `_series_derive` держит **`best_ever`** монотонно и переносит `last_break` вперёд: состояние
  помнит 400 цепочек (`SERIES_KEEP`), и без этого забывание старых цепочек молча укорачивало бы
  рекорд и стирало дату обрыва — то есть файл переставал бы отвечать на два из четырёх вопросов
  рамки, ничего об этом не сказав.

## 6. Границы и остатки

**Границы захода:** сортировка вмешательств и порог веса не тронуты; гард не изменён ни на строку;
демон не перезапускался; в рабочие таблицы не писалось; ничего не удалено (прежнее содержимое
файла лежит снимком и процитировано выше дословно); папка выкладки моста не тронута.

**ОСТАТКИ (на 10.08.2026, `docs/artifacts/2026-08-10-chain-series-state-file.md`):**

* **класс «фикс в git ≠ фикс в проде» ДЕЙСТВУЕТ** — счёт живёт в памяти демона, рестарт этим
  заданием запрещён; до рестарта боевой файл остаётся нулём, и первая настоящая сходимость
  измерится только после него;
* **сходимость на живом наборе цепочек ещё не измерена** — измерить её можно лишь после того, как
  живой счёт наберёт цепочки: смоделировать его реплеем нельзя по устройству (тело карточки живёт
  только в момент рождения, ради чего файл и заведён);
* **зеркала ПК-полосы нет** (точки касания: файл состояния ПК-демона, признак личности пишущего,
  вызов сверки);
* проверка формы судит одну черту записи (дата рождения) — подделка, аккуратно проставившая её,
  сверкой по форме не ловится; ловится она сверкой по исходу, и наоборот;
* сверка не сравнивает ВЕС (коммиты и рестарты) — порог веса вынесен в отдельный заход, и
  сравнивать его сейчас значило бы трогать то, что задание запретило.

установщик, прогон сверки с кодом возврата). Снимок очереди переиспользован из
